# 1. Purpose

This document records the physical architecture decisions made during the PostgreSQL Physical Architecture & Logical-to-Physical Mapping workstream.

Its purpose is to:

- record physical architecture decisions explicitly;
- preserve the reasoning behind those decisions;
- maintain traceability from requirements to physical implementation;
- distinguish proposed decisions from accepted decisions;
- prevent physical implementation choices from silently redefining the logical model;
- provide a controlled input to the final **P2-02.3 Physical Data Design**;
- provide a reusable architectural record for future implementation and review.

This document is a **decision log**, not the final physical database design.

It records the decisions and their rationale while the physical architecture is being established.

# 5. Decision Principles

All decisions in this workstream must follow these principles.

## 5.1 Logical Model Preservation

Physical implementation must preserve the approved logical semantics.

Physical convenience must not override logical meaning.

---

## 5.2 Requirements-Driven Design

Physical choices must be derived from:

1. governing standards;
2. platform architecture;
3. data-layer architecture;
4. approved logical model;
5. reconciled physical requirements.

Technology preference alone is insufficient justification.

---

## 5.3 Simplicity First

Prefer the simplest physical architecture that satisfies the requirements.

Avoid:

- unnecessary databases;
- unnecessary schemas;
- unnecessary extensions;
- speculative indexes;
- premature search infrastructure;
- premature AI infrastructure;
- unnecessary distributed architecture;
- unnecessary polyglot persistence.

---

## 5.4 Governance First

The physical design must protect:

- knowledge integrity;
- historical integrity;
- evidence traceability;
- provenance;
- governance history;
- version integrity.

---

## 5.5 One Primary Persistence Technology

The current architecture prefers one primary persistence technology unless a demonstrated requirement justifies another technology.

Additional databases or persistence technologies must therefore have explicit architectural justification.

---

## 5.6 Evidence Over Preference

Where multiple technically valid options exist, decisions should be evaluated using:

- requirements fit;
- correctness;
- governance;
- integrity;
- maintainability;
- operational complexity;
- performance;
- scalability;
- implementation practicality.

# 7. PAD-001 — Database Boundary

**Decision Area:** Database Boundary
**Status:** Accepted
**Decision Date:** 2026-08-27

## 7.1 Decision

The ASM Brain Knowledge Data Layer shall use a **dedicated PostgreSQL database** as its database boundary.

The Knowledge Data Layer shall not share its primary PostgreSQL database with unrelated application domains unless a future architectural decision explicitly establishes such sharing as necessary.

The dedicated database boundary provides a clear physical separation for the governed knowledge data layer while retaining PostgreSQL as the primary persistence technology established by the P2-02.3 physical design framework.

---

## 7.2 Context

The ASM Brain Knowledge Data Layer is a governed knowledge infrastructure rather than an ordinary application-content store.

The physical architecture therefore needs a database boundary that supports:

- controlled ownership;
- clear security boundaries;
- independent schema governance;
- controlled migrations;
- operational isolation;
- future scalability;
- clear responsibility for knowledge data.

The database boundary must also remain consistent with the broader ASM Brain architecture and the approved logical data model.

---

## 7.3 Source Basis

This decision is based on the following architectural sources:

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;
- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation.

The logical model defines the governed Knowledge Data Layer independently of application-specific data concerns.

The physical design therefore establishes a dedicated PostgreSQL database boundary rather than allowing unrelated application data to become part of the Knowledge Data Layer physical model.

---

## 7.4 Options Considered

### Option A — Dedicated PostgreSQL Database

**Assessment:** Preferred.

Create a dedicated PostgreSQL database for the ASM Brain Knowledge Data Layer.

Advantages:

- clear physical ownership boundary;
- simpler governance;
- clearer security and access control;
- controlled migration boundary;
- reduced coupling with unrelated application data;
- easier operational reasoning;
- preserves the Knowledge Data Layer as an independent architectural asset.

---

### Option B — Shared PostgreSQL Database

**Assessment:** Not selected for the baseline architecture.

A shared database could reduce infrastructure overhead, but would introduce a weaker physical boundary between the Knowledge Data Layer and unrelated application domains.

It could also increase:

- operational coupling;
- migration coupling;
- permission complexity;
- accidental cross-domain dependencies;
- long-term governance complexity.

The reduction in infrastructure complexity does not currently justify the weaker architectural boundary.

---

### Option C — Separate Database Technology

**Assessment:** Rejected for the baseline.

Introducing another database technology would add unnecessary operational and architectural complexity.

PostgreSQL has already been established as the primary database technology for this physical design workstream.

A separate persistence technology would therefore require a demonstrated requirement and an explicit future architecture decision.

---

## 7.5 Rationale

The dedicated database boundary provides a strong and understandable physical boundary around the ASM Brain Knowledge Data Layer.

It supports the project's governance-first approach without introducing unnecessary architectural complexity.

The decision also preserves future flexibility: the database can contain one or more controlled schemas if later decisions establish a need for additional physical separation within the Knowledge Data Layer.

The database boundary therefore remains intentionally broader than the schema boundary.

---

## 7.6 Consequences

### Positive

- strong physical isolation of governed knowledge data;
- clearer ownership and security boundaries;
- independent migration control;
- reduced coupling with unrelated application domains;
- simpler operational governance;
- clearer future infrastructure scaling boundary.

### Negative

- additional database provisioning and management;
- potentially higher infrastructure overhead than a shared database;
- cross-database access would require explicit architectural handling if ever needed.

---

## 7.7 Relationship to PAD-002

PAD-001 establishes the **database boundary**.

PAD-002 establishes the **schema boundary inside that database**.

Therefore:

    Dedicated PostgreSQL Database
            |
            +── ASM Brain Knowledge Data Layer Schema

The two decisions are complementary and should not be treated as alternatives.

---

## 7.8 Dependencies

PAD-001 is informed by:

- the PostgreSQL technology decision in the P2-02.3 Physical Design Decision Framework;
- the logical Knowledge Data Layer boundary defined by P2-02.2;
- the physical requirements reconciled for P2-02.3.

PAD-001 provides the boundary within which PAD-002 and subsequent physical decisions operate.

---

## 7.9 Acceptance Criteria

PAD-001 is considered ready for acceptance when:

- [x] A dedicated PostgreSQL database is defined for the ASM Brain Knowledge Data Layer.
- [x] The database boundary is distinct from unrelated application domains.
- [x] The decision remains consistent with the established PostgreSQL technology choice.
- [x] Database and schema boundaries are explicitly distinguished.
- [x] The decision does not require additional database technologies.
- [x] Architecture review completed.
- [x] Decision formally accepted into the final physical design.

# 8. PAD-002 — Schema Boundary

**Decision Area:** Schema Boundary  
**Status:** Accepted
**Decision Date:** 2026-08-27

## 8.1 Decision

The ASM Brain Knowledge Data Layer shall use **one dedicated PostgreSQL schema** within the dedicated PostgreSQL database established by PAD-001.

The baseline physical architecture shall therefore provide:

    Dedicated PostgreSQL Database
            |
            +── Dedicated ASM Brain Knowledge Data Layer Schema

The schema shall contain the governed physical objects required to implement the approved Knowledge Data Layer.

Additional schemas shall not be introduced into the baseline architecture without a demonstrated requirement and an explicit architecture decision.

---

## 8.2 Context

PAD-001 establishes the dedicated PostgreSQL database boundary for the ASM Brain Knowledge Data Layer.

The next physical boundary is the PostgreSQL schema.

The schema provides the immediate namespace, ownership, permission, and organizational boundary for the physical objects implementing the Knowledge Data Layer.

The baseline architecture should therefore establish a clear and simple schema structure without introducing additional physical segmentation before it is required.

---

## 8.3 Source Basis

This decision is based on:

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;
- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-001 — Database Boundary.

The approved logical model defines a coherent Knowledge Data Layer.

No current requirement establishes multiple PostgreSQL schemas within that layer.

---

## 8.4 Options Considered

### Option A — One Dedicated Schema

**Assessment:** Preferred.

Use one dedicated PostgreSQL schema for the ASM Brain Knowledge Data Layer.

Advantages:

- simple namespace;
- clear ownership;
- straightforward permission management;
- reduced migration complexity;
- fewer cross-schema dependencies;
- easier development and maintenance;
- sufficient separation for the current Knowledge Data Layer scope.

---

### Option B — Multiple Schemas by Domain

**Assessment:** Not selected for the baseline.

The Knowledge Data Layer contains multiple logical domains and concepts, but logical domain separation does not automatically require separate PostgreSQL schemas.

Using multiple schemas at this stage would introduce additional:

- namespace complexity;
- permission boundaries;
- migration considerations;
- cross-schema dependencies;
- operational overhead.

No demonstrated requirement currently justifies that complexity.

---

### Option C — Shared Application Schema

**Assessment:** Rejected for the baseline.

Placing the Knowledge Data Layer objects into a general application schema would weaken the physical boundary established by PAD-001.

It would also increase coupling between governed knowledge data and unrelated application structures.

---

## 8.5 Rationale

A single dedicated schema provides the simplest physical organization that satisfies the current requirements.

It preserves a clear boundary between:

- the ASM Brain Knowledge Data Layer; and
- unrelated database structures.

It also provides sufficient room for the initial physical implementation without prematurely fragmenting the database into multiple schemas.

The decision can be revisited if future requirements demonstrate a genuine need for additional schema boundaries.

---

## 8.6 Consequences

### Positive

- simple physical organization;
- clear namespace;
- straightforward permissions;
- simpler migrations;
- reduced cross-schema coupling;
- easier operational management;
- consistent with the current scope of the Knowledge Data Layer.

### Negative

- all baseline Knowledge Data Layer objects share one schema namespace;
- future schema-level separation, if required, will require a later architecture decision and potentially a migration.

---

## 8.7 Relationship to PAD-001

PAD-001 defines the database boundary.

PAD-002 defines the schema boundary inside that database.

Therefore:

            |
            +── ASM Brain Knowledge Data Layer Schema
                    |

The two decisions therefore address different concerns and should remain independently governed.

---

## 8.9 Dependencies

# 9. PAD-003 — Naming Conventions

**Decision Area:** Naming Conventions
**Status:** Accepted
**Decision Date:** 2026-08-27

## 9.1 Decision

PostgreSQL physical objects within the ASM Brain Knowledge Data Layer shall use:

- lowercase naming;
- `snake_case` word separation;
- singular nouns for entity/table names;
- domain-oriented names that reflect the governed logical concept;
- explicit, standardized names for constraints;
- explicit, standardized names for indexes.

Physical names shall remain understandable without requiring knowledge of application-specific abbreviations.

Names shall prioritize consistency, clarity, and long-term maintainability over brevity.

---

## 9.2 Table Naming

Tables representing governed entities shall use:

- lowercase;
- `snake_case`;
- singular nouns;
- names aligned with the corresponding logical entity.

Examples:

    knowledge_asset
    knowledge_asset_version
    taxonomy_concept

The physical table name should communicate the underlying governed concept rather than an application screen, API endpoint, or temporary implementation concern.

---

## 9.3 Column Naming

Columns shall use lowercase `snake_case`.

Examples:

    knowledge_asset_id
    knowledge_asset_version_id
    created_at
    updated_at

Column names should describe the data represented by the column and should avoid unnecessary abbreviations.

Where a column represents a relationship, its name should normally identify the referenced concept using the appropriate `_id` convention.

---

## 9.4 Primary Key Naming

Primary key columns should follow the entity identity convention.

For UUID-based governed entities, the preferred pattern is:

    <entity>_id

Examples:

    knowledge_asset_id
    knowledge_asset_version_id
    taxonomy_concept_id

Primary key constraint names shall use a consistent explicit convention.

Preferred pattern:

    pk_<table>

Example:

    pk_knowledge_asset

---

## 9.5 Foreign Key Naming

Foreign key columns shall normally use:

    <referenced_entity>_id

Where the relationship requires additional semantic qualification, the name should clearly communicate the role of the relationship.

Foreign key constraint names shall use:

    fk_<table>_<referenced_table>

The naming convention must remain deterministic and readable.

---

## 9.6 Unique Constraint Naming

Unique constraints shall use:

    uq_<table>_<column_or_columns>

Examples:

    uq_knowledge_asset_version_asset_sequence
    uq_taxonomy_concept_code

Where multiple columns participate in the uniqueness rule, the participating columns should be represented sufficiently to make the constraint identifiable.

---

## 9.7 Check Constraint Naming

Check constraints shall use:

    ck_<table>_<purpose>

The purpose portion should identify the business or integrity rule being enforced.

Example:

    ck_knowledge_asset_version_sequence_positive

The exact constraints will be determined by later physical design decisions.

---

## 9.8 Index Naming

Indexes shall use:

    ix_<table>_<column_or_purpose>

Examples:

    ix_knowledge_asset_version_knowledge_asset_id
    ix_knowledge_asset_current_version_id

Where an index exists for a specific access pattern rather than simply a column, the name should describe that purpose.

Index naming must remain deterministic and avoid arbitrary or generated names where explicit naming is practical.

---

## 9.9 Naming of Other PostgreSQL Objects

Other PostgreSQL objects introduced into the baseline architecture shall follow the same principles:

- lowercase;
- `snake_case`;
- explicit;
- deterministic;
- domain-oriented;
- documented where their naming is not self-evident.

No additional PostgreSQL object category is approved merely by defining a naming convention for it.

The introduction of additional object types remains subject to the relevant architecture decision.

---

## 9.10 Reserved Words and Ambiguous Names

Physical object names should avoid PostgreSQL reserved words where a clear alternative exists.

Names that are technically valid but semantically ambiguous should also be avoided.

The preferred name is the one that makes the physical model understandable to a future engineer reviewing the database without requiring historical project context.

---

## 9.11 Abbreviations

Unnecessary abbreviations shall be avoided.

An abbreviation may be used when it is:

- widely understood;
- consistently used throughout the architecture; or
- required by a well-established technical convention.

Project-specific abbreviations should not be introduced solely to shorten identifiers.

---

## 9.12 Rationale

Consistent naming reduces cognitive overhead across:

- database design;
- migrations;
- application development;
- debugging;
- documentation;
- data analysis;
- operations;
- future architecture review.

Using domain-oriented names also reinforces the project's core principle that the physical database represents governed knowledge rather than application-interface terminology.

Explicit constraint and index naming improves migration readability and operational troubleshooting.

---

## 9.13 Relationship to the Logical Model

Physical names should preserve the meaning of the approved logical model.

A physical implementation may use a PostgreSQL-compatible naming form, but it must not rename a logical concept in a way that changes or obscures its meaning.

For example:

    Knowledge Asset
            ↓
    knowledge_asset

    Knowledge Asset Version
            ↓
    knowledge_asset_version

    Taxonomy Concept
            ↓
    taxonomy_concept

This establishes a clear logical-to-physical naming relationship.

---

## 9.14 Relationship to Later PAD Decisions

PAD-003 establishes naming conventions.

It does not decide:

- which tables will exist beyond the already approved foundational entities;
- which columns each table will contain;
- which indexes are required;
- which constraints are required;
- which extensions are required.

Those decisions remain governed by subsequent PAD decisions and the final Physical Data Design.

In particular:

- PAD-005 governs identifier strategy;
- PAD-016 governs integrity constraint strategy;
- PAD-017 governs indexing strategy.

---

## 9.15 Consequences

### Positive

- consistent physical vocabulary;
- easier database navigation;
- clearer migrations;
- improved maintainability;
- easier troubleshooting;
- stronger logical-to-physical traceability;
- reduced naming ambiguity.

### Negative

- longer names may sometimes result compared with heavily abbreviated alternatives;
- naming discipline must be maintained consistently during implementation.

---

# 10. PAD-004 — PostgreSQL Extensions

**Decision Area:** PostgreSQL Extensions  
**Status:** Accepted  
**Decision Date:** 2026-08-27

## 10.1 Decision

No PostgreSQL extensions are approved for the **baseline physical architecture** of the ASM Brain Knowledge Data Layer.

A PostgreSQL extension may be introduced in the future only when:

- a demonstrated functional or operational requirement exists;
- the requirement cannot be adequately satisfied using PostgreSQL core capabilities;
- the extension has been evaluated for compatibility, security, maintenance, and operational impact; and
- the extension is explicitly approved through the appropriate architecture decision process.

The absence of an approved extension does not prohibit future extensions. It establishes that extensions are **not part of the baseline by default**.

---

## 10.2 Context

PostgreSQL provides a broad extension ecosystem covering capabilities such as:

- specialized data types;
- indexing;
- full-text search;
- geographic data;
- procedural languages;
- monitoring and administration;
- additional database functionality.

However, the availability of an extension does not by itself establish an architectural requirement.

The ASM Brain Knowledge Data Layer should avoid introducing additional database dependencies until they are justified by an actual requirement.

---

## 10.3 Source Basis

This decision is based on:

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;
- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;

# 11. PAD-005 — Identifier Strategy

**Decision Area:** Identifier Strategy  
**Status:** Accepted  
**Decision Date:** 2026-08-27

## 11.1 Decision

The core governed entities of the ASM Brain Knowledge Data Layer shall use **UUID-based identifiers**.

The baseline UUID identifier strategy applies specifically to:

- Knowledge Asset;
- Knowledge Asset Version;
- Taxonomy Concept.

The corresponding PostgreSQL physical identifiers shall use the following conceptual pattern:

    knowledge_asset_id
    knowledge_asset_version_id
    taxonomy_concept_id

The identifier strategy establishes stable entity identity independently of mutable descriptive attributes.

The exact PostgreSQL UUID generation mechanism and implementation details shall be finalized as part of the Physical Data Design and implementation decisions where required.

---

## 11.2 Context

The ASM Brain Knowledge Data Layer contains governed entities whose identities must remain stable across:

- version creation;
- content changes;
- lifecycle transitions;
- taxonomy evolution;
- application integrations;
- migration operations;
- historical retrieval.

Identity must therefore not depend on mutable business attributes such as:

- title;
- name;
- slug;
- code;
- language;
- lifecycle status;
- version sequence.

The identifier strategy should also support distributed generation and integration without requiring a central sequential identifier allocator.

---

## 11.3 Source Basis

This decision is based on:

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;
- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-008 — Foundational Entity Mapping;
- PAD-009 — Version Physical Representation.

The approved logical model distinguishes stable entity identity from mutable attributes and Version sequence.

---

## 11.4 Core Entity Identifier Mapping

The baseline mapping is:

| Logical Entity | Physical Entity | Identifier |
|---|---|---|
| Knowledge Asset | `knowledge_asset` | `knowledge_asset_id` |
| Knowledge Asset Version | `knowledge_asset_version` | `knowledge_asset_version_id` |
| Taxonomy Concept | `taxonomy_concept` | `taxonomy_concept_id` |

The identifiers represent entity identity.

They do not represent:

- version order;
- lifecycle state;
- publication state;
- language;
- taxonomy hierarchy position.

Those concerns remain separately modeled.

---

## 11.5 Options Considered

### Option A — UUID

**Assessment:** Preferred.

Use UUIDs for the identifiers of the three core governed entities.

Advantages:

- globally unique identity;
- stable identity independent of mutable attributes;
- suitable for distributed generation;
- avoids exposing sequential database identifiers as the primary public identity;
- supports integration across services and environments;
- does not require a central sequence allocator.

---

### Option B — Sequential Integer Identifiers

**Assessment:** Not selected for the core governed entities.

Sequential integers are simple and efficient, but they provide less suitable identity semantics for a governed knowledge system that may eventually integrate multiple services and environments.

They also expose sequential characteristics that are unnecessary for the core governed identity model.

This does not imply that every future physical object must use UUIDs.

---

### Option C — Natural / Business Keys

**Assessment:** Rejected as the primary identity mechanism.

Attributes such as:

- slug;
- code;
- title;
- external identifier;

may change or may not remain globally unique.

They should therefore not become the primary identity of the core governed entities.

Such attributes may still receive appropriate uniqueness constraints when required by later physical decisions.

---

## 11.6 UUID and Version Sequence Are Different

The UUID identifies the Version record.

The Version sequence identifies the Version's order within its parent Knowledge Asset.

For example:

    Knowledge Asset
          |
          +── Version UUID A — sequence 1
          +── Version UUID B — sequence 2
          +── Version UUID C — sequence 3

The UUID must remain stable even if the Version becomes:

- current;
- superseded;
- retired;
- historically referenced.

The sequence must not be used as the Version's primary identity.

---

## 11.7 UUID and Human-Readable Identifiers

UUIDs are machine-oriented identifiers.

The physical model may also contain human-readable attributes such as:

- slug;
- code;
- name;
- title.

Those attributes serve different purposes.

They should not replace the stable UUID identity of the core governed entities.

Where human-readable identifiers require uniqueness, the relevant rule shall be established through the appropriate later physical decision.

---

## 11.8 UUID Generation

PAD-005 establishes the identifier type and identity strategy.

It does not yet prescribe a specific UUID-generation mechanism.

The final implementation should select a supported PostgreSQL/application generation approach based on:

- deployment architecture;
- PostgreSQL capabilities;
- migration requirements;
- operational simplicity;
- application integration.

No PostgreSQL extension is required solely because UUID identifiers are used.

---

## 11.9 Rationale

UUIDs provide a strong stable identity model for the core governed entities without coupling identity to mutable business data.

They are particularly appropriate for a knowledge platform where records may be:

- versioned;
- referenced by other governed entities;
- synchronized across systems;
- retained historically;
- exposed through APIs.

Separating UUID identity from Version sequence also preserves the logical distinction between **what a Version is** and **where that Version occurs in the Version history**.

---

### Positive

- stable core entity identity;
- strong integration capability;
- suitability for distributed systems;
- separation of identity from mutable attributes;
- preservation of Version identity across lifecycle changes;
- clear logical-to-physical mapping.

### Negative

- UUIDs are larger than typical integer identifiers;
- UUID values are less human-readable;
- indexing and storage characteristics must be considered in the eventual physical design.

These implementation considerations do not invalidate the architectural identifier decision.

# 12. PAD-006 — Schema Ownership

**Decision Area:** Schema Ownership  
**Status:** Accepted  
**Decision Date:** 2026-08-27

## 12.1 Decision

The ASM Brain Knowledge Data Layer PostgreSQL schema and its structural database objects shall be owned by a **controlled non-runtime database identity**.

Runtime application identities shall not own the schema or its structural objects.

Runtime identities shall receive only the database privileges required for their approved application responsibilities.

Structural ownership and runtime access shall therefore remain separate.

---

## 12.2 Context

The Knowledge Data Layer is a governed data asset.

The identity that owns database structures has significant authority over:

- schemas;
- tables;
- constraints;
- indexes;
- sequences or related database objects;
- other structural objects.

Allowing a normal runtime application identity to own those structures would create an unnecessary coupling between application execution and database administration.

A compromised or incorrectly configured runtime identity could potentially gain greater structural authority than required.

The physical architecture should therefore establish a clear separation between:

**structural ownership**

and

**runtime application access**.

---

## 12.3 Source Basis

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;

- PAD-007 — Migration Boundary.

The physical architecture requires controlled ownership and migration of the governed Knowledge Data Layer structures.

## 12.4 Ownership Boundary

The baseline ownership model is:

    Controlled Non-Runtime Identity
                |
                +── Owns Knowledge Data Layer Schema
                |
                +── Owns Structural Database Objects
                |
                +── Controlled structural changes

                     ↓

    Runtime Application Identity
                |
                +── Required application privileges only

# 13. PAD-007 — Migration Boundary

**Decision Area:** Migration Boundary  
**Status:** Accepted  
**Decision Date:** 2026-08-27

## 13.1 Decision

All structural changes to the ASM Brain Knowledge Data Layer PostgreSQL database shall be managed through **version-controlled, reviewable, repeatable migrations**.

Runtime application behavior shall not modify the database schema as part of normal application operation.

Structural changes shall therefore be:

- explicitly defined;
- version controlled;
- reviewable;
- repeatable across environments;
- attributable to a specific migration;
- executed through the controlled deployment process.

The migration mechanism shall be treated as the authoritative path for evolving the physical database structure.

---

## 13.2 Context

The ASM Brain Knowledge Data Layer is a governed knowledge infrastructure.

Its database structure must therefore remain:

- reproducible;
- auditable;
- consistent across environments;
- traceable to approved architectural decisions;
- recoverable through version-controlled artifacts.

Allowing application startup or runtime code to silently create or alter database structures would weaken those properties.

A controlled migration boundary is therefore required between:

**application behavior**

and

**database structure**.

---

## 13.3 Source Basis

This decision is based on:

- P2-02.1 — Knowledge Data Layer Architecture & Data Model Foundation;
- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-006 — Schema Ownership.

The physical architecture requires controlled structural change management.

---

## 13.4 What Constitutes a Structural Change

For this decision, structural changes include changes such as:

- creating or removing tables;
- creating or removing schemas;
- adding or removing columns;
- changing column definitions;
- creating or removing primary keys;
- creating or removing foreign keys;
- creating or removing unique constraints;
- creating or removing check constraints;
- creating or removing indexes;
- changing database object ownership;
- introducing approved PostgreSQL extensions;
- other changes that alter the database's physical structure.

Data changes performed as part of normal application operation are not automatically structural migrations.

---

## 13.5 Migration Characteristics

A migration should be:

### Version-Controlled

The migration definition shall exist in the project's version-controlled source.

### Reviewable

Structural changes shall be reviewable before being applied to the governed database.

### Repeatable

The migration process should be reproducible across controlled environments.

### Ordered

Migrations shall have an explicit ordering mechanism so that database structure can be established deterministically.

### Traceable

A deployed database structure should be traceable to the migration history that produced it.

---

## 13.6 Options Considered

### Option A — Version-Controlled Migration System

**Assessment:** Preferred.

Use a controlled migration mechanism in which structural changes are represented by versioned migration artifacts.

Advantages:

- reproducibility;
- auditability;
- reviewability;
- environment consistency;
- clear deployment history;
- controlled rollback/recovery planning.

---

### Option B — Automatic Schema Modification by Application

**Assessment:** Rejected.

Allowing application startup or runtime code to create or modify production schema would blur the boundary between application behavior and infrastructure management.

Potential problems include:

- unexpected production changes;
- difficult troubleshooting;
- insufficient review;
- environment drift;
- excessive runtime privileges;
- unclear change history.

---

### Option C — Manual Database Administration

**Assessment:** Not selected as the baseline.

Manual SQL changes can be useful for controlled operational emergencies, but they should not be the normal mechanism for evolving the Knowledge Data Layer schema.

Manual structural changes create a risk of divergence between:

- the deployed database;
- the migration history;
- the version-controlled physical design.

---

## 13.7 Migration and Runtime Separation

The baseline boundary is:

    Architecture Decision
            ↓
    Physical Design
            ↓
    Version-Controlled Migration
            ↓
    Controlled Deployment
            ↓
    PostgreSQL Structure

Separately:

    Application Runtime
            ↓
    Approved Data Operations
            ↓
    PostgreSQL Data

The application runtime shall not become an uncontrolled source of schema evolution.

- title;
- slug.

The identity therefore remains stable even when the Version's state changes.

---

## 15.6 Parent Relationship

Every `knowledge_asset_version` shall have a mandatory relationship to its parent `knowledge_asset`.

Conceptually:

    knowledge_asset
            |
            +── one or more
                    |
                    +── knowledge_asset_version

A Version without a parent Knowledge Asset is not valid within the governed Knowledge Data Layer.

The exact PostgreSQL foreign-key implementation is governed by the later Integrity Constraint Strategy.

---

## 15.7 Version Sequence

Each Version shall have an ordered sequence within its parent Knowledge Asset.

Conceptually:

    Knowledge Asset A
        ├── Version 1
        ├── Version 2
        └── Version 3

The Version sequence shall be:

- ordered within the parent;
- unique within the parent;
- independent of the UUID identity.

The same sequence value may therefore exist under different Knowledge Assets without creating a global conflict.

For example:

    Knowledge Asset A → Version 1
    Knowledge Asset B → Version 1

is valid.

---

## 15.8 Historical Version Preservation

Historical Versions shall remain independently addressable.

A later Version shall not overwrite the physical record of an earlier Version.

For example:

    Version 1 → preserved
    Version 2 → preserved
    Version 3 → current

Version 1 and Version 2 remain addressable even after Version 3 becomes current.

This preserves the historical integrity of the governed knowledge record.

---

## 15.9 Version Sequence and UUID Separation

The Version UUID and Version sequence serve different purposes.

**UUID**

Identifies the Version record.

**Version sequence**

Identifies the Version's ordinal position within its parent Knowledge Asset.

Therefore:

    Version UUID ≠ Version Sequence

The sequence must not be used as the primary identity of the Version.

---

## 15.10 Options Considered

### Option A — Separate Version Entity with UUID and Per-Parent Sequence

**Assessment:** Preferred.

Represent every Version as a separate `knowledge_asset_version` record with:

- UUID identity;
- parent Knowledge Asset;
- ordered Version sequence.

Advantages:

- preserves historical records;
- supports stable Version references;
- provides clear Version ordering;
- separates identity from sequence;
- supports current-Version protection;
- aligns directly with the logical model.

---

### Option B — Store Only the Latest Version

**Assessment:** Rejected.

Replacing the previous Version would destroy historical state and make governed historical reconstruction impossible.

This conflicts with the Knowledge Data Layer's version-governance requirements.

---

### Option C — Store Version History as a JSON or Embedded Structure

**Assessment:** Rejected for the baseline.

Embedding Version history inside the parent Knowledge Asset would weaken:

- independent Version identity;
- relationship integrity;
- queryability;
- indexing options;
- historical governance.

It would also make the physical representation less faithful to the logical model.

---

### Option D — Use Version Sequence as the Primary Key

**Assessment:** Rejected.

A Version sequence is only unique within a Knowledge Asset.

It is therefore not sufficient as a globally stable entity identity.

The UUID remains the Version identity.

---

## 15.11 Rationale

A governed knowledge platform must be able to distinguish the stable identity of a Knowledge Asset from the historical states through which it evolves.

A dedicated Version entity provides that separation cleanly.

The per-parent Version sequence provides human-understandable ordering without sacrificing stable UUID identity.

Preserving historical Version records also establishes the physical foundation required for later decisions concerning:

- current Version;
- lifecycle;
- governance;
- audit;
- evidence;
- provenance.

---

## 15.12 Consequences

### Positive

- complete Version history can be retained;
- historical Versions remain addressable;
- Version identity is stable;
- Version ordering is explicit;
- current-Version logic can be implemented separately;
- logical and physical models remain aligned.

### Negative

- Version history increases the number of database records;
- queries requiring current Version data may require an explicit relationship or lookup;
- additional integrity and indexing rules are required.

These consequences are expected and acceptable for the governed Version model.

# 16. PAD-010 — Current-Version Protection

**Decision Area:** Current-Version Protection
**Status:** Accepted
**Decision Date:** 2026-08-29

## 16.1 Decision

The current Version of a Knowledge Asset shall be represented by an explicit parent-level reference from:

`knowledge_asset`

to:

`knowledge_asset_version`

The reference shall identify the Version that is currently designated as the Knowledge Asset's current Version.

The referenced Version must belong to the same Knowledge Asset.

Conceptually:

    knowledge_asset
          |
          +── current_version_id
                    |
                    ↓
          knowledge_asset_version
                    |
                    +── knowledge_asset_id
                    |
                    +── version_sequence

The physical design shall therefore prevent a Knowledge Asset from identifying a Version belonging to a different Knowledge Asset as its Current Version.

Historical Versions shall remain independently addressable regardless of which Version is currently designated as Current.

---

## 16.2 Context

PAD-009 established that Knowledge Asset Version is a distinct physical entity with:

- its own UUID identity;
- a mandatory parent Knowledge Asset relationship;
- a per-parent Version sequence;
- independently addressable historical records.

The physical model therefore needs an explicit and reliable mechanism for identifying which Version is currently active for a Knowledge Asset.

Simply deriving the Current Version by assuming that the highest Version sequence is current would create an implicit rule rather than an explicit physical relationship.

The architecture requires the Current Version to be represented directly.

---

## 16.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-005 — Identifier Strategy;
- PAD-008 — Foundational Entity Mapping;
- PAD-009 — Version Physical Representation.

The logical model distinguishes the Knowledge Asset from its Versions and requires the Knowledge Asset to be able to identify its current Version.

PAD-010 establishes the corresponding physical representation.

---

## 16.4 Current-Version Representation

The baseline physical model is:

    knowledge_asset
        |
        +── knowledge_asset_id
        |
        +── current_version_id ──────────┐
                                         |
                                         ↓
                              knowledge_asset_version
                                         |
                                         +── knowledge_asset_version_id
                                         +── knowledge_asset_id
                                         +── version_sequence

The Current Version is therefore a property of the Knowledge Asset.

It is not a property of the Version record itself.

A Version does not become Current merely because of its own attributes.

The parent Knowledge Asset explicitly identifies which Version is Current.

---

## 16.5 Same-Parent Requirement

The Current Version reference must satisfy the following invariant:

> The Version referenced by `knowledge_asset.current_version_id` must have the same parent `knowledge_asset_id` as the referencing Knowledge Asset.

For example:

    Knowledge Asset A
        ├── Version 1
        ├── Version 2  ← Current
        └── Version 3

is valid.

But:

    Knowledge Asset A
        └── current_version_id → Version belonging to Knowledge Asset B

is invalid.

This same-parent requirement is a core integrity rule of the physical representation.

---

## 16.6 Why Explicit Current-Version Reference

An explicit parent-level Current Version reference provides:

- deterministic identification of the Current Version;
- direct navigation from Knowledge Asset to Current Version;
- independence from Version sequence;
- clear historical preservation;
- predictable application behavior;
- a physical integrity target that can be enforced.

It also avoids requiring every application query to infer Current Version through ordering or lifecycle attributes.

---

## 16.7 Current Version Is Not the Same as Latest Version

The Current Version shall not be defined merely as:

> the Version with the highest `version_sequence`.

The latest Version and Current Version may normally coincide, but they represent different concepts.

For example:

    Version 1 → historical
    Version 2 → current
    Version 3 → later-created but not yet current

The architecture must therefore retain the ability to distinguish Version chronology from Current-Version designation.

The explicit reference established by PAD-010 provides that distinction.

---

## 16.8 Historical Version Preservation

Changing the Current Version shall not delete, overwrite, or mutate the historical Version records merely because they are no longer Current.

For example:

    Before:
        Version 2 ← Current

    After:
        Version 3 ← Current

Version 2 remains an independently addressable historical record.

The Current-Version reference changes; the historical Version records remain preserved.

---

## 16.9 Options Considered

### Option A — Parent-Level Current Version Reference

**Assessment:** Preferred.

Store an explicit Current Version reference on `knowledge_asset`.

Advantages:

- deterministic;
- direct;
- clear semantic ownership;
- efficient lookup;
- supports historical preservation;
- allows Current Version to differ from latest Version;
- provides a concrete integrity rule.

---

### Option B — Derive Current Version from Maximum Version Sequence

**Assessment:** Rejected.

The maximum Version sequence represents Version ordering, not necessarily Current-Version designation.

Using it as the Current-Version mechanism would couple two distinct concepts and prevent the architecture from representing a non-latest Version as Current when required.

---

### Option C — Store a Current Flag on Every Version

**Assessment:** Not selected.

A `current` flag on `knowledge_asset_version` could represent the state, but it creates a distributed invariant:

> exactly one Version belonging to each Knowledge Asset must be Current.

That approach requires additional enforcement and creates a wider opportunity for inconsistent state.

The parent-level reference provides a clearer ownership model for the Current-Version designation.

---

### Option D — Store Current Version Only in Application State

**Assessment:** Rejected.

Current Version is governed data and must not depend solely on application memory, cache state, or derived application logic.

The database must contain the authoritative Current-Version relationship.

---

## 16.10 Integrity Requirement

The physical design must enforce the same-parent rule.

The final implementation should ensure that:

    knowledge_asset.current_version_id

cannot reference a `knowledge_asset_version` whose:

    knowledge_asset_id

belongs to another Knowledge Asset.

The exact PostgreSQL constraint mechanism is intentionally deferred to:

**PAD-016 — Integrity Constraint Strategy**

PAD-010 establishes the required invariant.

PAD-016 will determine the precise physical enforcement mechanism.

---

## 16.11 Transitional / Initialization Consideration

The Current Version relationship may require special consideration during initial creation of a Knowledge Asset and its first Version.

The final transaction and initialization behavior shall ensure that the database cannot be left in an invalid governed state.

This concern will be addressed through:

- PAD-016 — Integrity Constraint Strategy;
- PAD-018 — Transaction Strategy;
- PAD-020 — Initialization Strategy.

PAD-010 does not prescribe the exact creation sequence.

---

## 16.12 Rationale

The Current Version is a governed property of the Knowledge Asset.

Representing it explicitly at the parent level provides the clearest physical expression of that relationship while preserving the independent identity and history of Version records.

The same-parent invariant is essential because a simple foreign key to `knowledge_asset_version` alone does not, by itself, communicate the semantic requirement that the referenced Version belongs to the same Knowledge Asset.

Therefore, the architecture must treat the same-parent relationship as an explicit integrity requirement.

---

## 16.13 Consequences

### Positive

- deterministic Current-Version lookup;
- explicit physical representation;
- strong historical preservation;
- separation of Version ordering from Current designation;
- clear integrity requirement;
- supports future application and API access patterns.

### Negative

- introduces a parent-to-Version reference in addition to the Version-to-parent relationship;
- requires a carefully designed integrity constraint;
- requires deliberate handling during initial creation and Version transitions.

These costs are accepted because Current-Version integrity is a core requirement of the governed Version model.

---

## 16.14 Relationship to PAD-009

PAD-009 establishes:

> `knowledge_asset_version` as the physical Version entity.

PAD-010 establishes:

> `knowledge_asset.current_version_id` as the explicit Current-Version relationship.

Therefore PAD-010 depends directly on PAD-009.

---

## 16.15 Relationship to PAD-016

PAD-010 defines the required integrity invariant.

PAD-016 will determine how PostgreSQL enforces that invariant.

The separation is intentional:

    PAD-010
    What must be true
          ↓
    PAD-016
    How the database enforces it

This prevents the architectural decision from prematurely locking the implementation to a particular constraint technique.

---

## 16.16 Relationship to PAD-018 and PAD-020

Current-Version changes may require coordinated transactional behavior.

PAD-018 will determine the broader transaction strategy.

Initial creation and establishment of a valid Current Version will be considered under PAD-020.

PAD-010 therefore establishes the invariant while leaving execution sequencing to later decisions.

---

## 16.17 Scope Boundary

PAD-010 does not decide:

- exact PostgreSQL foreign-key syntax;
- deferrable/non-deferrable constraint behavior;
- transaction boundaries;
- concurrency control;
- initialization workflow;
- application API behavior;
- Version lifecycle semantics.

Those concerns remain explicitly governed by subsequent decisions.

---

## 16.18 Acceptance Criteria

PAD-010 is considered ready for acceptance when:

- [x] Current Version is represented by an explicit reference from `knowledge_asset`.
- [x] The reference targets `knowledge_asset_version`.
- [x] The referenced Version must belong to the same Knowledge Asset.
- [x] Historical Versions remain independently addressable.
- [x] Current Version is not derived solely from maximum Version sequence.
- [x] Current Version is not represented solely through application state.
- [x] The same-parent integrity requirement is explicitly defined.
- [x] Exact integrity enforcement is deferred to PAD-016.
- [x] Transaction considerations are deferred to PAD-018.
- [x] Initialization considerations are deferred to PAD-020.
- [x] Architecture review completed.
- [x] Decision formally accepted into the final physical design.

# 17. PAD-011 — Lifecycle Representation

**Decision Area:** Lifecycle Representation  
**Status:** Accepted 
**Decision Date:** 2026-08-29

## 17.1 Decision

The lifecycle state of a Knowledge Asset Version shall be represented explicitly as governed data in the PostgreSQL physical model.

Lifecycle state shall be associated with the **Knowledge Asset Version**, rather than being represented solely as an application-derived condition.

The baseline physical representation shall provide a dedicated lifecycle-state attribute on `knowledge_asset_version`.

The lifecycle-state value shall be controlled by an explicitly defined set of permitted states.

The exact lifecycle state vocabulary, transition rules, and enforcement mechanism shall remain aligned with the approved logical model and shall be finalized through the appropriate physical and governance decisions.

Lifecycle state shall remain distinct from:

- Version sequence;
- Current-Version designation;
- publication state;
- governance status;
- evidence or provenance status.

---

## 17.2 Context

Knowledge Asset Versions move through a lifecycle as they are created, reviewed, approved, published, superseded, or otherwise governed.

The physical model therefore needs to preserve lifecycle state as explicit governed information.

Lifecycle state should not be inferred solely from:

- Version sequence;
- timestamps;
- whether a Version is Current;
- application memory;
- publication records.

Explicit representation provides a stable basis for querying, governance, validation, and future workflow implementation.

---

## 17.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-008 — Foundational Entity Mapping;
- PAD-009 — Version Physical Representation;
- PAD-010 — Current-Version Protection.

The logical model treats lifecycle as a governed aspect of the Version.

PAD-011 establishes its physical representation without redefining the approved lifecycle model.

---

## 17.4 Lifecycle Ownership

Lifecycle state belongs to the Knowledge Asset Version.

Conceptually:

    knowledge_asset
          |
          +── knowledge_asset_version
                    |
                    +── lifecycle_state

This reflects the fact that different Versions of the same Knowledge Asset may occupy different lifecycle states.

For example:

    Version 1 → superseded
    Version 2 → approved
    Version 3 → draft

The lifecycle state therefore cannot be represented solely at the parent Knowledge Asset level.

---

## 17.5 Lifecycle State and Current Version

Lifecycle state and Current-Version designation are separate concepts.

For example:

    Version 1 → superseded
    Version 2 → approved
    Version 3 → draft

The Current Version relationship established by PAD-010 identifies the Version currently designated by the Knowledge Asset.

Lifecycle state describes the governed state of an individual Version.

Therefore:

    Current Version ≠ Lifecycle State

A Version may be Current because the Knowledge Asset explicitly designates it as Current, while its lifecycle state is governed independently.

The precise compatibility rules between Current-Version designation and lifecycle states shall be established through later governance and integrity decisions where required.

---

## 17.6 Lifecycle State and Version Sequence

Version sequence establishes ordering within a Knowledge Asset.

Lifecycle state establishes the governed state of a Version.

They therefore serve different purposes.

For example:

    Version 1 → sequence 1 → superseded
    Version 2 → sequence 2 → approved
    Version 3 → sequence 3 → draft

The lifecycle state shall not be derived from the Version sequence.

---

## 17.7 Lifecycle State and Publication State

Lifecycle state shall not automatically be treated as publication state.

A Version may be:

- approved but not yet published;
- published and later superseded;
- in draft while undergoing review.

Therefore the physical architecture shall not assume:

    lifecycle_state = publication_state

If publication requires a distinct governed representation, that concern shall be handled through the appropriate later physical design.

---

## 17.8 Lifecycle State Representation

The baseline physical model shall include a dedicated lifecycle-state attribute associated with `knowledge_asset_version`.

Conceptually:

    knowledge_asset_version
        |
        +── knowledge_asset_version_id
        +── knowledge_asset_id
        +── version_sequence
        +── lifecycle_state

The exact PostgreSQL data type and permitted-value enforcement mechanism remain implementation details to be finalized through the physical design and integrity strategy.

---

## 17.9 Lifecycle Vocabulary

The lifecycle-state vocabulary must be explicitly governed.

The physical implementation shall not permit arbitrary uncontrolled lifecycle values.

The final vocabulary should be derived from the approved logical model rather than invented independently at the PostgreSQL layer.

If the approved logical model is subsequently revised, the corresponding physical lifecycle representation shall be reconciled through the architecture decision process.

---

## 17.10 Options Considered

### Option A — Explicit Lifecycle State on Knowledge Asset Version

**Assessment:** Preferred.

Represent lifecycle state directly on `knowledge_asset_version`.

Advantages:

- explicit;
- queryable;
- independently addressable;
- aligned with Version ownership;
- supports governance workflows;
- avoids deriving lifecycle state from unrelated attributes.

---

### Option B — Derive Lifecycle State from Other Attributes

**Assessment:** Rejected.

Inferring lifecycle from timestamps, Version sequence, Current-Version status, or other attributes would make the lifecycle model implicit and fragile.

It would also make lifecycle behavior harder to govern and validate.

---

### Option C — Store Lifecycle State Only in Application Logic

**Assessment:** Rejected.

Lifecycle state is governed knowledge metadata and must remain represented in the authoritative Knowledge Data Layer.

Application logic may implement workflows around lifecycle state, but it shall not become the sole source of lifecycle truth.

---

### Option D — Store Lifecycle State Only at Knowledge Asset Level

**Assessment:** Rejected.

Different Versions of the same Knowledge Asset may have different lifecycle states.

Representing lifecycle only at the parent level would therefore lose Version-level lifecycle information.

---

## 17.11 Rationale

Lifecycle is an attribute of a Version's governed state.

Representing it explicitly on `knowledge_asset_version` preserves the distinction between:

- what the Version is;
- where it occurs in Version history;
- whether it is Current;
- what lifecycle state it occupies.

This separation prevents several unrelated concepts from becoming coupled through implicit application rules.

---

## 17.12 Consequences

### Positive

- explicit lifecycle information;
- clear Version-level ownership;
- easier lifecycle queries;
- better governance support;
- reduced dependence on application-derived state;
- clear separation from Current-Version designation.

### Negative

- lifecycle values require governance;
- lifecycle transitions require validation;
- future workflow rules may require additional constraints or supporting structures.

These consequences are expected for a governed lifecycle model.

---

## 17.13 Relationship to PAD-009

PAD-009 establishes `knowledge_asset_version` as the physical Version entity.

PAD-011 adds lifecycle representation to that Version entity.

Therefore PAD-011 depends directly on PAD-009.

---

## 17.14 Relationship to PAD-010

PAD-010 establishes the explicit Current-Version relationship.

PAD-011 establishes Version lifecycle state.

These are intentionally separate:

    PAD-010
    Current Version
          ≠
    PAD-011
    Lifecycle State

Any rules governing which lifecycle states may be Current will be handled through later integrity and governance decisions.

---

## 17.15 Relationship to PAD-016

PAD-011 establishes that lifecycle state must use a controlled set of permitted values.

PAD-016 will determine the appropriate database-level integrity mechanisms for enforcing the relevant physical rules.

PAD-011 therefore defines the architectural requirement without prematurely selecting the exact PostgreSQL constraint mechanism.

---

## 17.16 Scope Boundary

PAD-011 does not yet decide:

- the final lifecycle-state vocabulary if not already fixed by the logical model;
- complete lifecycle transition rules;
- workflow implementation;
- publication workflow;
- approval workflow;
- audit history of lifecycle transitions;
- exact PostgreSQL data type;
- exact constraint implementation.

Those concerns remain governed by the appropriate logical, physical, governance, or implementation decisions.

- [x] Lifecycle state is distinct from publication state.

# 18. PAD-012 — Multilingual Representation

**Decision Area:** Multilingual Representation  
**Status:** Accepted
**Decision Date:** 2026-08-29

## 18.1 Decision

Multilingual representation shall be supported through language-specific physical records associated with the appropriate governed entity while preserving stable identity across languages. 

For Knowledge Asset content, language-specific representations shall be associated with the appropriate Knowledge Asset Version. Language shall not create a separate Knowledge Asset identity by default and shall not replace Version identity. 

For Taxonomy Concepts, language-specific representations shall be associated with the same stable Taxonomy Concept identity. Different language representations shall therefore describe the same governed conceptual identity rather than creating separate Taxonomy Concepts. 

The physical model shall treat language as governed structured data rather than as separate fixed language-specific columns or uncontrolled free-form JSON. 

The exact physical table structure, language-code representation, uniqueness rules, and localization attributes shall be determined during Physical Data Design.
### Scope Boundary
This decision establishes multilingual representation as a physical architecture requirement but does not prescribe the final language-specific table, column, or constraint design. 

The detailed Physical Data Design shall determine the appropriate representation while preserving stable Knowledge Asset, Knowledge Asset Version, and Taxonomy Concept identities across supported languages.

---

## 18.2 Context

ASM Brain is intended to support structured medical knowledge that may be represented in multiple languages, including Bangla and English.

The physical architecture must therefore support multilingual content without:

- duplicating the underlying Knowledge Asset identity;
- creating separate Knowledge Assets merely because the language differs;
- embedding multiple languages into uncontrolled text fields;
- coupling language identity to Version identity.

A multilingual representation should remain associated with the governed Version from which it derives.

---

## 18.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-008 — Foundational Entity Mapping;
- PAD-009 — Version Physical Representation;
- PAD-011 — Lifecycle Representation.

The logical model requires multilingual representation while preserving stable Knowledge Asset and Version identity.

PAD-012 establishes the physical architectural direction without finalizing every multilingual attribute or supporting table.

---

## 18.4 Multilingual Representation Principle

The baseline relationship is:

    knowledge_asset
          |
          +── knowledge_asset_version
                    |
                    +── language representation
                    |
                    +── language representation
                    |
                    +── language representation

For example:

    Knowledge Asset A
        |
        +── Version 3
              |
              +── Bangla representation
              +── English representation

The language representations belong to the Version.

They do not become separate Knowledge Assets solely because they use different languages.

---

## 18.5 Language and Knowledge Asset Identity

Language shall not determine Knowledge Asset identity.

For example:

    Bangla version of a concept
    English version of the same concept

does not automatically mean:

    Knowledge Asset A
    Knowledge Asset B

Instead, where the logical model defines them as representations of the same governed knowledge, they remain associated with the same Knowledge Asset and relevant Version.

This preserves stable identity across languages.

---

## 18.6 Language and Version Identity

Language shall not replace Version identity.

A Version remains independently identifiable through:

`knowledge_asset_version_id`

Language identifies a representation associated with that Version.

Conceptually:

    knowledge_asset_version_id
              |
              +── language = bn
              |
              +── language = en

The exact cardinality and uniqueness rules shall be defined through later integrity and relationship decisions.

---

## 18.7 Language as Governed Metadata

Language values shall be controlled rather than stored as arbitrary free-form text.

The final implementation should use an explicitly governed language representation compatible with the approved logical model.

The physical design should be capable of distinguishing at least the languages required by the product scope without preventing future supported languages from being introduced through controlled change.

---

## 18.8 Avoiding Language Duplication

The physical architecture should avoid duplicating the stable structural identity of a Knowledge Asset merely to represent another language.

For example, the following should generally remain one governed asset:

    Knowledge Asset
        |
        +── Version
              |
              +── Bangla representation
              +── English representation

rather than:

    Knowledge Asset — Bangla
    Knowledge Asset — English

unless the logical model explicitly defines them as separate governed entities.

---

## 18.9 Multilingual Content and Versioning

Language-specific representations are associated with a particular Knowledge Asset Version.

Therefore, when the governed knowledge changes materially and a new Version is created, the multilingual representations of that Version must be handled according to the Version's own governance rules.

The physical model must not imply that changing one language automatically changes the historical Version of another language.

This preserves the independent historical integrity of Version records.

---

## 18.10 Options Considered

### Option A — Language-Specific Representation Associated with Version

**Assessment:** Preferred.

Represent language-specific content as separate representations associated with the relevant Knowledge Asset Version.

Advantages:

- supports multiple languages;
- preserves stable Knowledge Asset identity;
- preserves Version identity;
- supports language-specific retrieval;
- avoids uncontrolled multilingual fields;
- supports future language expansion.

---

### Option B — Multiple Language Columns in `knowledge_asset_version`

**Assessment:** Rejected for the baseline.

A structure such as:

    title_bn
    title_en
    summary_bn
    summary_en

would couple the physical schema to a fixed language set.

Adding another language would require structural schema changes rather than adding governed data.

It also becomes increasingly difficult to maintain as the number of multilingual attributes grows.

---

### Option C — Separate Knowledge Asset for Each Language

**Assessment:** Rejected where the logical model defines the content as the same governed knowledge.

This would unnecessarily duplicate entity identity and weaken cross-language relationships.

---

### Option D — Store All Languages in a JSON Structure

**Assessment:** Not selected for the baseline.

JSON can represent multilingual values, but using it as the primary multilingual model would weaken:

- explicit language governance;
- relational integrity;
- queryability;
- indexing options;
- predictable physical structure.

# 19. PAD-013 — Relationship Representation

**Decision Area:** Relationship Representation
**Status:** Accepted
**Decision Date:** 2026-08-29

## 19.1 Decision

Relationships between governed Knowledge Data Layer entities shall be represented explicitly through relational structures rather than being encoded solely through application logic, uncontrolled text fields, or opaque embedded data.

The physical architecture shall preserve the relationship boundaries established by the approved logical model.

Where a relationship is:

- many-to-many;
- independently governed;
- attributed with relationship-specific metadata; or
- required to remain independently addressable;

the relationship shall be represented through a dedicated PostgreSQL relationship entity.

Where a relationship is a simple mandatory or optional parent-child association, it may be represented through a foreign-key relationship on the dependent entity.

The exact physical relationship structures shall be determined from the approved logical model and finalized through the physical data design.

PAD-013 establishes the relationship representation principle; it does not pre-approve a specific relationship table for every logical relationship.

---

## 19.2 Context

ASM Brain is a structured knowledge platform rather than a collection of isolated records.

Knowledge Assets, Knowledge Asset Versions, Taxonomy Concepts, evidence, provenance, governance information, and other governed entities may have relationships that are important to the meaning and integrity of the knowledge.

These relationships must therefore be represented in a way that remains:

- explicit;
- queryable;
- enforceable;
- traceable to the logical model;
- maintainable over time.

The physical architecture should avoid hiding governed relationships inside application code or arbitrary serialized structures.

---

## 19.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-008 — Foundational Entity Mapping;
- PAD-009 — Version Physical Representation;
- PAD-012 — Multilingual Representation.

P2-02.2 is authoritative for the logical relationships.

PAD-013 translates those approved relationships into a physical representation principle without redefining their logical meaning.

---

## 19.4 Relationship Representation Principle

The baseline physical principle is:

    Logical relationship
            ↓
    Explicit relational representation
            ↓
    PostgreSQL foreign key(s)
    or
    dedicated relationship entity

The physical representation shall be selected according to the cardinality and governance requirements of the logical relationship.

---

## 19.5 Simple Parent-Child Relationships

A simple parent-child relationship may be represented through a foreign key on the dependent entity.

For example:

    knowledge_asset
          |
          +── knowledge_asset_version

The parent relationship established by PAD-009 is therefore represented through the Version's relationship to its Knowledge Asset.

Similarly, the physical representation of other dependent entities may use foreign keys where the logical relationship does not require an independently governed relationship entity.

---

## 19.6 Many-to-Many Relationships

Many-to-many relationships shall not be represented through:

- comma-separated identifiers;
- delimited text;
- repeated columns;
- uncontrolled JSON arrays;
- application-only mappings.

Where the logical model requires a many-to-many relationship, the baseline physical architecture shall represent it through an explicit relationship entity.

Conceptually:

    Entity A
       |
       +── relationship entity ──+
                                 |
                                 ↓
                              Entity B

This allows both sides of the relationship to remain explicitly identifiable and supports database-level integrity.

---

## 19.7 Relationship-Specific Attributes

Where a relationship itself has governed attributes, those attributes shall belong to the relationship representation rather than being attached arbitrarily to either endpoint.

For example, if a relationship has:

- relationship type;
- ordering;
- role;
- effective dates;
- provenance;
- governance metadata;

the physical model should represent those attributes on the relationship structure where appropriate.

This prevents relationship-specific meaning from being confused with entity-level attributes.

---

## 19.8 Knowledge Asset and Taxonomy Concept Relationships

Relationships between Knowledge Assets or Versions and Taxonomy Concepts shall be represented explicitly according to the approved logical model.

The physical design shall not encode taxonomy membership merely as:

- a free-text taxonomy name;
- a comma-separated list;
- an application-only mapping.

Where taxonomy assignment is many-to-many or carries relationship-specific metadata, a dedicated relationship structure shall be used.

The exact relationship structure is deferred to the detailed physical data design.

---

## 19.9 Version-Level Relationship Boundary

Relationships that are logically associated with a particular Knowledge Asset Version shall remain attached to the Version boundary.

The physical model shall not silently move Version-specific relationships to the parent `knowledge_asset` merely for implementation convenience.

This preserves historical meaning.

For example:

    Knowledge Asset
        |
        +── Version 1 → Taxonomy relationship
        |
        +── Version 2 → different Taxonomy relationship

may legitimately represent different governed states.

The final physical structure shall follow the logical model's specified relationship ownership.

---

## 19.10 Relationship Identity

A relationship entity that requires independent governance or addressability shall have its own identity according to the applicable identifier strategy.

The relationship's identity shall not automatically be derived solely from display values.

Where a relationship is purely associative and does not require independent identity, a composite uniqueness rule may be appropriate.

The exact identity approach shall be finalized during detailed physical design and integrity analysis.

---

## 19.11 Relationship History

Where a relationship is Version-specific, historical relationship state shall remain consistent with the Version to which it belongs.

A later Version shall not silently mutate the historical relationship state of an earlier Version.

This is particularly important for governed knowledge relationships whose meaning may change between Versions.

---

## 19.12 Options Considered

### Option A — Explicit Relational Representation

**Assessment:** Preferred.

Represent governed relationships through foreign keys or dedicated relationship entities according to their logical cardinality and governance requirements.

Advantages:

- explicit;
- queryable;
- enforceable;
- traceable;
- compatible with PostgreSQL relational integrity;
- supports future indexing and performance optimization.

---

### Option B — Application-Only Relationships

**Assessment:** Rejected.

Relationships that exist only in application code are difficult to audit, query, validate, and govern.

The database should retain authoritative relationship information.

---

### Option C — Delimited Identifier Lists

**Assessment:** Rejected.

Storing multiple identifiers in text fields weakens:

- referential integrity;
- queryability;
- indexing;
- data validation.

It is not suitable for governed relational knowledge.

---

### Option D — General-Purpose JSON Relationship Storage

**Assessment:** Not selected for the baseline.

JSON may be appropriate for specific flexible payloads where separately justified, but it shall not be the default representation for governed relational relationships.

---

## 19.13 Rationale

Relationships are part of the meaning of structured knowledge.

Representing them explicitly allows the database to preserve the logical model while providing a foundation for:

- referential integrity;
- queryability;
- indexing;
- governance;
- historical reconstruction.

The architecture therefore prefers relational representation while allowing simple relationships to remain simple foreign-key relationships rather than creating unnecessary relationship tables.

---

## 19.14 Consequences

### Positive

- explicit relationship semantics;
- stronger integrity;
- easier querying;
- improved traceability;
- support for complex relationships;
- better preservation of Version-specific historical state.

### Negative

- additional relational structures may be required;
- relationship-heavy queries may require joins;
- detailed relationship design requires careful mapping from the logical model.

These consequences are acceptable because relationship integrity is fundamental to the structured knowledge architecture.

It does not add or redefine foundational entities established by PAD-008.

# 20. PAD-014 — Evidence & Provenance Representation

**Status:** Accepted
**Decision Date:** 2026-08-29

Evidence and Provenance shall be represented as explicit governed physical structures rather than being reduced to free-text citations, URLs, or application logs.

Evidence and Provenance representations shall preserve the applicable Knowledge Asset and Knowledge Asset Version boundaries so that historical governed knowledge remains traceable to the appropriate supporting evidence and provenance context.

The physical design shall support structured Evidence and Provenance information while avoiding premature commitment to a specific evidence-association granularity. The final Physical Data Design shall determine whether a particular Evidence or Provenance association is required at Knowledge Asset level, Knowledge Asset Version level, assertion or claim level, or through another explicitly justified relationship structure, based on the approved logical model and applicable Evidence Standard requirements

A separate claim or assertion entity shall not be introduced solely because it appears convenient for Evidence or Provenance modelling. Any such entity shall require an explicit logical-model or physical-design justification.

URLs, citation strings, and application logs may be attributes or supporting references where appropriate, but shall not constitute the complete Evidence or Provenance model.

It does not finalize:

- the exact Provenance table structure;

Those details shall be resolved during Physical Data Design using the approved logical model, physical requirements, and applicable Evidence Standard.

# 21. PAD-015 — Governance & Audit Representation

**Decision Area:** Governance & Audit Representation
**Status:** Accepted
**Decision Date:** 2026-08-29

## 21.1 Decision

Governance state and Audit history shall be represented as distinct but related physical concerns within the ASM Brain Knowledge Data Layer.

Governance representation shall capture the **current governed state and control metadata** required by the approved logical model.

Audit representation shall preserve a **historical record of relevant governed actions and changes** required for traceability and accountability.

The physical architecture shall not treat Audit history as merely a set of current-state attributes on the governed entity.

Likewise, Governance state shall not depend solely on reconstructing the current state from an audit log.

Where required by the logical model, governance metadata shall be associated with the appropriate governed entity or Version.

Audit records shall identify the governed object and the relevant event or change sufficiently to support traceability.

The exact physical entities, attributes, retention rules, event vocabulary, and integrity mechanisms shall be finalized through the detailed Physical Data Design and subsequent implementation decisions.

---

## 21.2 Context

ASM Brain is a governed knowledge platform.

Knowledge Assets and Versions may undergo activities such as:

- creation;
- modification;
- review;
- approval;
- publication;
- supersession;
- retirement;
- other governed state changes.

The system must therefore distinguish between:

**current governance state**

and

**historical record of what happened**.

For example:

    Current Governance State
        Version 4 → approved

versus:

    Audit History
        Version 1 → created
        Version 1 → reviewed
        Version 1 → superseded
        Version 2 → created
        Version 2 → approved
        Version 3 → created
        Version 4 → approved

These are different information requirements and should not be collapsed into a single physical concept.

---

## 21.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-011 — Lifecycle Representation;
- PAD-014 — Evidence & Provenance Representation.

The logical model establishes governance and audit as important aspects of the governed knowledge system.

PAD-015 establishes their physical architectural boundary.

---

## 21.4 Governance Representation Principle

Governance information shall represent the current governed state or control metadata applicable to the relevant entity.

Examples may include:

- governance status;
- approval state;
- ownership;
- review state;
- publication eligibility;
- other controlled governance metadata defined by the logical model.

Governance attributes shall be associated with the entity to which they logically belong.

The physical model shall not automatically place every governance attribute on `knowledge_asset` or `knowledge_asset_version` without reference to the approved logical model.

---

## 21.5 Audit Representation Principle

Audit information shall preserve relevant historical events or changes affecting governed data.

An Audit record should be capable of establishing, where required:

- what governed object was affected;
- what type of event occurred;
- when it occurred;
- which actor or process performed it;
- sufficient context to support later investigation.

Audit records therefore represent historical events rather than merely current state.

---

## 21.6 Governance State vs Audit History

The baseline distinction is:

    Governance
        ↓
    "What is the governed state now?"

    Audit
        ↓
    "What happened to produce or change that state?"

Governance state should be directly queryable without replaying the entire audit history.

Audit history should remain independently available for historical traceability.

---

## 21.7 Audit and Version History

Audit history and Knowledge Asset Version history are related but not identical.

Version history answers questions such as:

> Which Version exists?

Audit history answers questions such as:

> What happened to the Version, and who or what performed the relevant action?

Therefore:

    Version History ≠ Audit History

PAD-009 governs Version preservation.

PAD-015 governs the audit representation around governed activities.

---

## 21.8 Governance and Lifecycle

PAD-011 establishes lifecycle state on the Version.

PAD-015 does not replace lifecycle state with audit events.

For example:

    lifecycle_state = approved

represents current state.

An audit history may separately record:

    draft → review
    review → approved

The audit history provides historical traceability while lifecycle state provides the current governed state.

---

## 21.9 Governance and Evidence/Provenance

PAD-014 establishes Evidence and Provenance.

PAD-015 does not use Audit to replace Provenance.

For example:

- Provenance answers where information originated or how it was derived.
- Audit answers what governed action occurred within the system.

These concepts shall remain distinct.

---

## 21.10 Actor Representation

Where auditability is required, the audit representation should identify the actor responsible for the event.

The actor may be:

- a human user;
- an administrative identity;
- an application process;
- an automated workflow;
- another governed system identity.

The physical model should distinguish actor identity from the event itself.

The exact actor model remains subject to detailed physical design.

---

## 21.11 Audit Event Representation

Audit events should be represented in a structured manner rather than as arbitrary narrative text.

Conceptually:

    audit_event
        |
        +── governed_object
        +── event_type
        +── occurred_at
        +── actor
        +── context

The exact entity name and attributes are not finalized by PAD-015.

---

## 21.12 Audit Immutability Principle

Audit history should be treated as append-oriented historical information.

Normal application behavior should not modify historical audit events merely to reflect a later current state.

If correction of an audit record is ever required, it should occur through an explicitly governed operational process rather than silent mutation.

The exact immutability mechanism remains an implementation concern.

---

## 21.13 Options Considered

### Option A — Separate Governance State and Audit History

**Assessment:** Preferred.

Maintain current governance information separately from historical audit information.

Advantages:

- clear semantics;
- direct current-state access;
- preserved historical traceability;
- simpler governance queries;
- clearer accountability model.

---

### Option B — Reconstruct Current Governance State Entirely from Audit

**Assessment:** Rejected.

Replaying historical events to determine current state would unnecessarily couple normal application queries to audit history.

It also increases complexity and makes current-state access less direct.

---

### Option C — Store Audit Information Only as Timestamps and User Columns

**Assessment:** Rejected as the complete audit model.

Fields such as:

    created_at
    created_by
    updated_at
    updated_by

can provide useful operational metadata, but they do not constitute a complete historical audit trail.

---

### Option D — Store Governance and Audit in One Undifferentiated Structure

**Assessment:** Rejected.

Combining current governance state with historical audit events would blur their semantics and make both governance queries and historical analysis harder.

---

## 21.14 Rationale

Governance and audit answer different questions.

A governed knowledge system needs to know both:

- the current state of an object; and
- the history of relevant actions that affected it.

Keeping these concerns distinct provides clearer semantics, simpler access patterns, and stronger long-term traceability.

This also prevents the audit log from becoming the accidental source of truth for current governance state.

---

- preserved audit history;
- direct current-state queries;
- improved accountability;
- clearer distinction between lifecycle, provenance, and audit;
- better support for future governance workflows.

### Negative

- additional physical structures may be required;
- governance and audit data must be maintained consistently;
- audit retention may increase storage requirements;
- detailed actor and event design requires additional work.

These consequences are acceptable for a governed medical knowledge platform.

# 22. PAD-016 — Integrity Constraint Strategy

**Decision Area:** Integrity Constraint Strategy
**Status:** Accepted
**Decision Date:** 2026-08-29

## 22.1 Decision

The ASM Brain Knowledge Data Layer shall use PostgreSQL database-level integrity constraints as a primary mechanism for enforcing structural and relational invariants that can be reliably expressed at the database layer.

The physical architecture shall prefer declarative PostgreSQL constraints over application-only validation for rules that are fundamentally properties of the stored data.

The baseline integrity strategy shall use, where appropriate:

- `PRIMARY KEY` constraints;
- `FOREIGN KEY` constraints;
- `UNIQUE` constraints;
- `NOT NULL` constraints;
- `CHECK` constraints;
- appropriate exclusion or other PostgreSQL-native mechanisms only where a demonstrated requirement exists.

Application-level validation shall complement, but shall not replace, database-level enforcement of authoritative structural invariants.

Integrity rules that require transactional coordination across multiple records shall be enforced through an appropriate combination of constraints and transaction strategy rather than relying solely on application behavior.

The exact constraint definitions for individual entities shall be finalized during detailed Physical Data Design and migration implementation.

---

## 22.2 Context

The ASM Brain Knowledge Data Layer is the authoritative structured storage layer for governed knowledge.

A database schema is not sufficiently reliable if important structural rules exist only in application code.

Several decisions already established requirements that must ultimately be enforced at the physical level.

Examples include:

- unique entity identity;
- mandatory parent relationships;
- unique Version sequence within a Knowledge Asset;
- controlled lifecycle values;
- valid taxonomy relationships;
- valid Evidence relationships;
- appropriate Governance relationships;
- Current-Version consistency.

PAD-016 establishes the common integrity strategy for these requirements.

---

## 22.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-003 — Naming Conventions;
- PAD-005 — Identifier Strategy;
- PAD-007 — Migration Boundary;
- PAD-009 — Version Physical Representation;
- PAD-010 — Current-Version Protection;
- PAD-011 — Lifecycle Representation;
- PAD-012 — Multilingual Representation;
- PAD-013 — Relationship Representation;
- PAD-014 — Evidence & Provenance Representation;
- PAD-015 — Governance & Audit Representation.

PAD-016 consolidates the database-level integrity philosophy established by these decisions.

---

## 22.4 Integrity Principle

The baseline principle is:

    Authoritative structural invariant
                    ↓
        PostgreSQL-level enforcement
                    ↓
       Application validation as
       complementary protection

The database should prevent invalid states whenever the rule can be expressed reliably and appropriately at the database layer.

Application validation remains important for:

- user experience;
- business workflow;
- early error detection;
- complex rules unsuitable for database enforcement.

However, application validation shall not be considered sufficient protection for authoritative structural invariants.

---

## 22.5 Primary Key Integrity

Every governed physical entity requiring independent identity shall have an appropriate primary key.

For the core governed entities established by PAD-005:

- `knowledge_asset`;
- `knowledge_asset_version`;
- `taxonomy_concept`;

the approved UUID identifier strategy shall be enforced through primary-key constraints.

The exact primary-key definitions shall be finalized in the physical schema.

---

## 22.6 Foreign-Key Integrity

Foreign keys shall be used to enforce required relational references between governed entities.

For example:

    knowledge_asset_version
            |
            +── knowledge_asset_id
                       |
                       ↓
                knowledge_asset

The database shall prevent references to non-existent parent entities unless an explicitly justified physical design requires another mechanism.

Foreign-key behavior such as `ON DELETE` and `ON UPDATE` shall be selected according to the lifecycle and governance requirements of each relationship.

---

## 22.7 Uniqueness Integrity

Where the logical or physical model requires a value or combination of values to be unique, the database shall enforce that uniqueness.

PAD-009 provides a direct example:

    knowledge_asset_id
    +
    version_sequence

shall be unique within the Knowledge Asset.

Likewise, multilingual representation may require a uniqueness rule for:

    Version
    +
    Language

if that cardinality is established by the logical model.

Exact uniqueness constraints shall be finalized during detailed physical design.

---

## 22.8 Required-Value Integrity

Attributes that are mandatory according to the logical or physical model shall be represented using appropriate `NOT NULL` constraints where database-level enforcement is applicable.

A value shall not be made nullable merely because the application currently expects to supply it.

Nullability shall reflect the actual domain requirement.

Optional values shall remain nullable only where absence has valid domain meaning.

---

## 22.9 Domain and Controlled-Value Integrity

Controlled values such as lifecycle state and language identifiers shall not be treated as unrestricted arbitrary text where the logical model requires a governed vocabulary.

The database should provide appropriate integrity protection for such values.

The exact mechanism may include:

- `CHECK` constraints;
- reference tables;
- other justified relational mechanisms.

PAD-016 establishes the requirement for enforcement but does not prematurely select the final mechanism for every controlled vocabulary.

---

## 22.10 Current-Version Integrity

PAD-010 establishes that the Knowledge Asset maintains an explicit Current-Version relationship.

The physical integrity strategy shall ensure, to the extent expressible at the database level, that:

    knowledge_asset.current_version_id

refers to a Version belonging to the same Knowledge Asset.

The final implementation mechanism shall be selected during detailed physical design.

Where enforcement requires transactional coordination or a specialized constraint pattern, PAD-018 and the implementation design shall address the required behavior.

---

## 22.11 Lifecycle Integrity

PAD-011 establishes lifecycle state as governed Version data.

The integrity strategy shall prevent invalid lifecycle-state values from entering the authoritative data layer.

Where lifecycle transition rules require historical or cross-record logic, they shall not automatically be forced into a simple `CHECK` constraint.

Instead:

- static domain validity may use database constraints;
- transition workflows may use controlled application/service logic;
- transactional invariants may use appropriate database mechanisms.

This preserves a useful boundary between data integrity and workflow behavior.

---

## 22.12 Relationship Integrity

PAD-013 establishes explicit relational representation.

Foreign keys and appropriate uniqueness constraints shall protect relational integrity.

The database shall prevent orphaned relationship records where the relationship requires valid endpoints.

Many-to-many relationships shall receive appropriate composite or surrogate identity and uniqueness rules according to their logical semantics.

---

## 22.13 Evidence and Provenance Integrity

PAD-014 establishes Evidence and Provenance as governed structured information.

Their physical relationships shall therefore receive appropriate database-level referential integrity.

The database should prevent Evidence or Provenance records from referencing non-existent governed entities where such relationships are authoritative.

Exact relationship constraints remain subject to detailed physical design.

---

## 22.14 Governance and Audit Integrity

PAD-015 establishes Governance and Audit as distinct concerns.

Governance records shall receive appropriate relational and domain integrity.

Audit history shall receive appropriate structural protection consistent with its historical and append-oriented nature.

Integrity enforcement shall not imply that normal application behavior may freely rewrite historical audit records.

The exact audit immutability mechanism remains outside the scope of PAD-016.

---

## 22.15 Constraint Naming

All database constraints shall follow the naming conventions established by PAD-003.

Constraint names shall be:

- deterministic;
- descriptive;
- consistent;
- unique within the applicable PostgreSQL namespace.

The physical naming standard shall be applied consistently to:

- primary keys;
- foreign keys;
- unique constraints;
- check constraints;
- other approved constraint types.

---

## 22.16 Application Validation vs Database Integrity

Application validation and database integrity serve complementary purposes.

### Application Validation

Responsible for:

- user-facing validation;
- workflow validation;
- early feedback;
- complex business rules;
- contextual decisions.

### Database Integrity

Responsible for:

- authoritative structural invariants;
- referential integrity;
- uniqueness;
- mandatory values;
- controlled domains;
- persistence-level consistency.

The application shall not assume that validation performed before a database write guarantees the final database state.

---

## 22.17 Constraint Timing

Constraints shall be evaluated according to PostgreSQL capabilities and the requirements of the specific invariant.

Where immediate enforcement is appropriate, normal immediate constraints should be preferred.

Deferred enforcement should be introduced only where a demonstrated transactional requirement exists.

The physical design shall avoid unnecessary deferred constraints because they complicate transaction behavior and reasoning.

---

## 22.18 Options Considered

### Option A — Database-Level Declarative Integrity

**Assessment:** Preferred.

Use PostgreSQL constraints wherever the invariant can be expressed clearly and reliably.

Advantages:

- authoritative;
- centralized;
- consistent;
- protected from alternative application paths;
- easier to audit;
- reduces invalid persisted states.

---

### Option B — Application-Only Validation

**Assessment:** Rejected as the baseline.

Application validation can be bypassed by:

- another service;
- administrative tooling;
- migration scripts;
- future applications;
- direct database operations.

Structural integrity therefore cannot depend solely on application code.

---

### Option C — Trigger-Heavy Integrity Model

**Assessment:** Not selected for the baseline.

Triggers can solve certain complex integrity problems, but widespread trigger use increases:

- hidden behavior;
- debugging complexity;
- migration complexity;
- operational surprises.

Triggers should therefore be introduced only where declarative constraints and transaction design cannot appropriately express the required invariant.

---

### Option D — No Database-Level Integrity

**Assessment:** Rejected.

This would make the Knowledge Data Layer vulnerable to invalid or inconsistent states and would weaken the authority of the database as the structured knowledge store.

---

## 22.18 Rationale

The Knowledge Data Layer must remain trustworthy regardless of which application or operational process writes to it.

Database-level integrity provides a durable enforcement boundary for structural truths.

At the same time, not every business or workflow rule belongs inside PostgreSQL.

The strategy therefore deliberately balances:

    declarative database integrity
            +
    application/service validation
            +
    transaction coordination where necessary

This avoids both extremes:

- a weak database with integrity only in application code;
- an over-engineered database containing all application workflow logic.

---

## 22.19 Consequences

### Positive

- stronger authoritative data integrity;
- reduced invalid persisted states;
- protection across multiple application paths;
- clearer separation of database and application responsibilities;
- easier long-term maintenance.

### Negative

- additional schema complexity;
- migrations must carefully manage constraints;
- some cross-record rules require deeper transaction or physical-design analysis;
- overly complex constraints can become difficult to maintain.

These trade-offs are accepted in favor of a trustworthy governed data layer.

---

## 22.20 Relationship to PAD-018

Some integrity requirements depend on transaction boundaries and multi-record operations.

PAD-016 establishes the integrity requirement.

PAD-018 will determine the transaction strategy needed to preserve those invariants during writes.

---

## 22.21 Relationship to PAD-019

Concurrency can affect whether an integrity rule remains valid when multiple operations occur simultaneously.

PAD-016 establishes the required invariant.

PAD-019 will determine the concurrency strategy needed to protect it under concurrent operations.

---

## 22.22 Scope Boundary

PAD-016 does not yet finalize:

- every individual table constraint;
- exact foreign-key actions;
- complete controlled-vocabulary implementation;
- exact Current-Version enforcement mechanism;
- trigger implementation;
- audit immutability implementation;
- transaction isolation level;
- locking strategy;
- complete index strategy.

Those concerns remain subject to detailed Physical Data Design and the corresponding PAD decisions.

- [x] Primary-key integrity is required for independently identified entities.

# 23. PAD-017 — Indexing Strategy

**Decision Area:** Indexing Strategy
**Status:** Accepted
**Decision Date:** 2026-08-29

## 23.1 Decision

The ASM Brain Knowledge Data Layer shall use a deliberate, access-pattern-driven PostgreSQL indexing strategy.

Indexes shall be created to support:

- primary-key access;
- required uniqueness;
- foreign-key relationship access where appropriate;
- established or expected high-value query patterns;
- sorting and filtering patterns that provide demonstrated benefit;
- governance, lifecycle, Version, taxonomy, evidence, and other approved access requirements.

The baseline physical architecture shall avoid indiscriminate indexing of every column.

Indexes shall be treated as physical performance structures rather than additional sources of business truth.

Every non-required index should have an identifiable access-pattern or performance justification.

The final index set shall be determined through detailed Physical Data Design and validated against realistic query patterns and expected data volume.

---

## 23.2 Context

The ASM Brain Knowledge Data Layer is expected to support structured queries across:

- Knowledge Assets;
- Knowledge Asset Versions;
- Taxonomy Concepts;
- multilingual representations;
- relationships;
- Evidence and Provenance;
- Governance and Audit information.

Some of these structures will become frequently queried relationship and filtering paths.

However, unnecessary indexes introduce costs:

- additional storage;
- slower writes;
- greater migration complexity;
- additional maintenance;
- increased operational complexity.

The indexing strategy therefore needs to balance read performance against write and maintenance costs.

---

## 23.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-003 — Naming Conventions;
- PAD-005 — Identifier Strategy;
- PAD-009 — Version Physical Representation;
- PAD-010 — Current-Version Protection;
- PAD-013 — Relationship Representation;
- PAD-016 — Integrity Constraint Strategy.

PAD-017 translates known access and integrity requirements into an indexing principle without prematurely defining the complete index inventory.

---

## 23.4 Indexing Principle

The baseline principle is:

    Query / access requirement
              ↓
       physical access path
              ↓
          appropriate index

rather than:

    column exists
         ↓
    create index

Index selection shall therefore be driven by how the data is accessed.

---

## 23.5 Primary-Key Indexes

PostgreSQL primary-key constraints provide the required uniqueness and corresponding index support.

The physical design shall rely on the primary-key mechanism rather than creating duplicate indexes for the same identity requirement.

For example:

    knowledge_asset_id
    knowledge_asset_version_id
    taxonomy_concept_id

will receive primary-key support through their respective primary-key constraints.

Duplicate indexes serving the same purpose shall be avoided.

---

## 23.6 Unique Constraints and Indexes

Where uniqueness is required, a `UNIQUE` constraint should normally be preferred over creating an independent index solely to enforce uniqueness.

For example, PAD-009 establishes the requirement that:

    knowledge_asset_id
    +
    version_sequence

be unique within a Knowledge Asset.

The physical design should normally express this requirement through an appropriate unique constraint.

The resulting PostgreSQL index can then support both integrity and access.

---

## 23.7 Foreign-Key Access

Foreign-key relationships establish structural integrity, but the existence of a foreign key does not automatically mean that PostgreSQL creates a supporting index on the referencing column.

The physical design shall evaluate foreign-key columns for indexing based on:

- parent lookup patterns;
- join frequency;
- delete/update behavior;
- expected cardinality;
- query workload.

Indexes shall therefore be added where the relationship is an important access path or where operational behavior demonstrates a need.

---

## 23.8 Version Access Patterns

Knowledge Asset Version queries are expected to include access patterns such as:

    Knowledge Asset
        →
    ordered Versions

and:

    Knowledge Asset
        →
    Current Version

The physical design should therefore evaluate indexes supporting:

- Version retrieval by `knowledge_asset_id`;
- ordering by Version sequence;
- lookup of the Current Version relationship;
- historical Version access.

The exact composite indexes shall be finalized during detailed Physical Data Design.

---

## 23.9 Lifecycle Access Patterns

PAD-011 establishes lifecycle state as explicit Version data.

If operational and governance workflows frequently query Versions by lifecycle state, appropriate indexes should be considered.

However, a lifecycle column shall not automatically receive an index merely because it exists.

Index selection should consider:

- cardinality;
- selectivity;
- query frequency;
- combined filtering patterns.

---

## 23.10 Multilingual Access Patterns

PAD-012 establishes language-specific representations.

The physical design should support common access patterns such as:

    Version
      +
    Language

Where the logical model requires one representation per language for a Version, the corresponding uniqueness rule may also provide useful index support.

Additional indexes should be added only where actual query patterns justify them.

---

## 23.11 Relationship Indexing

Relationship entities commonly require indexes supporting both directions of traversal.

For example:

    Entity A
       ↓
    relationship
       ↓
    Entity B

may require efficient access for:

    A → B

and:

    B → A

The detailed physical design shall evaluate both access directions for many-to-many relationship structures.

---

## 23.12 Evidence and Provenance Indexing

Evidence and Provenance structures may require indexes supporting:

- lookup by associated Version;
- lookup by source;
- lookup by relevant governed entity;
- common evidence retrieval patterns.

The exact index inventory shall be determined from the logical relationships and expected query workload.

---

## 23.13 Governance and Audit Indexing

Governance structures should be indexed according to their operational access patterns.

Audit structures may require indexes supporting queries such as:

- events for a governed object;
- events by time;
- events by actor;
- events by event type.

Audit indexing shall consider the expected growth of historical data.

The physical design should avoid creating excessive indexes on append-heavy audit structures because each additional index increases write cost.

---

## 23.14 Composite Index Principle

Composite indexes should be used where a recurring query pattern filters or joins on multiple columns in a meaningful order.

The column order shall reflect the expected access pattern.

Composite indexes shall not be created merely because several columns are frequently present in a table.

---

## 23.15 Partial Indexes

Partial indexes may be considered where:

- only a subset of rows is frequently queried;
- the predicate is stable and meaningful;
- the performance benefit justifies the additional physical complexity.

Partial indexes shall not be introduced into the baseline without a demonstrated access-pattern requirement.

---

## 23.16 Indexes and Constraints

Where a constraint already provides an appropriate supporting index, a duplicate index shall not be created.

The physical design should identify:

- indexes created by primary keys;
- indexes created by unique constraints;
- independently created performance indexes.

This avoids unnecessary duplication.

---

## 23.17 Index Naming

All independently defined indexes shall follow the naming convention established by PAD-003.

Index names shall be:

- deterministic;
- descriptive;
- consistent;
- unique within the applicable PostgreSQL namespace.

The naming convention shall allow maintainers to understand the table and indexed purpose without relying on generated PostgreSQL names.

---

## 23.18 Index Lifecycle and Migrations

Indexes shall be managed through the migration boundary established by PAD-007.

Changes to indexes shall be:

- version-controlled;
- reviewable;
- repeatable;
- reversible where practical.

Index changes shall be treated as physical schema changes.

Production index operations that may require special operational handling shall be addressed during implementation planning.

---

## 23.19 Index Validation

Index decisions shall be validated against realistic access patterns.

Where the system reaches sufficient data volume and representative workload, query plans and execution performance should be reviewed.

The architecture shall allow indexes to be added, modified, or removed based on evidence rather than speculation.

---

## 23.20 Options Considered

### Option A — Access-Pattern-Driven Indexing

**Assessment:** Preferred.

Create indexes based on integrity requirements and meaningful query/access patterns.

---

### Option B — Index Every Foreign Key

**Assessment:** Not selected as an absolute rule.

Foreign-key columns are important candidates, but automatic indexing of every foreign key can create unnecessary indexes.

The final decision should consider actual access and operational behavior.

---

### Option C — Index Every Queryable Column

**Assessment:** Rejected.

This creates unnecessary storage and write overhead and does not guarantee useful query performance.

---

### Option D — Minimal Primary-Key-Only Indexing

**Assessment:** Rejected.

The Knowledge Data Layer will require efficient relationship, filtering, ordering, and governance access beyond primary-key lookups.

---

## 23.21 Rationale

Indexes are performance structures and should therefore be designed around actual access patterns.

A disciplined indexing strategy provides a balance between:

- read performance;
- write performance;
- storage;
- maintenance;
- operational simplicity.

This approach also allows the index inventory to evolve as real workload evidence becomes available.

---

## 23.22 Consequences

### Positive

- targeted query performance;
- reduced unnecessary storage;
- lower write overhead;
- easier physical maintenance;
- evidence-based optimization.

### Negative

- detailed workload analysis is required;
- some indexes may need to be introduced later;
- performance tuning remains an ongoing operational activity.

These trade-offs are accepted.

PAD-017 applies that naming standard to the physical index strategy.

---

## 23.24 Relationship to PAD-009

---

PAD-018 will establish transaction strategy.

# 24. PAD-018 — Transaction Strategy

**Decision Area:** Transaction Strategy
**Status:** Accepted
**Decision Date:** 2026-08-29

## 24.1 Decision

The ASM Brain Knowledge Data Layer shall use PostgreSQL transactions as the authoritative unit of atomic persistence for operations that modify related governed data.

A logical operation that requires multiple related database changes to become valid together shall be committed as a single transaction.

The transaction strategy shall ensure that:

- all required changes for a governed operation succeed together; or
- none of those changes become part of the committed database state.

Transactions shall be kept appropriately scoped to the logical operation they represent.

The baseline architecture shall prefer straightforward transaction boundaries and shall avoid unnecessarily long-running transactions.

Transaction strategy shall work together with:

- database integrity constraints defined by PAD-016;
- indexing decisions defined by PAD-017;
- concurrency controls defined by PAD-019.

The exact transaction boundaries for individual workflows shall be finalized during application and physical implementation design.

---

## 24.2 Context

ASM Brain contains relationships in which a logical operation may require changes to multiple physical records.

Examples may include:

- creating a Knowledge Asset and its initial Version;
- creating a Version and its associated multilingual representation;
- changing a Current-Version relationship;
- creating or updating governed relationships;
- recording governance state changes;
- creating Evidence or Provenance relationships;
- recording corresponding audit information.

Allowing only part of such an operation to be committed could leave the Knowledge Data Layer in an inconsistent state.

PostgreSQL transactions provide the required atomicity boundary.

---

## 24.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-007 — Migration Boundary;
- PAD-009 — Version Physical Representation;
- PAD-010 — Current-Version Protection;
- PAD-013 — Relationship Representation;
- PAD-014 — Evidence & Provenance Representation;
- PAD-015 — Governance & Audit Representation;
- PAD-016 — Integrity Constraint Strategy;
- PAD-017 — Indexing Strategy.

PAD-018 establishes the transaction principle without prematurely specifying application workflow implementation.

---

## 24.4 Atomicity Principle

The baseline principle is:

    Logical operation
          |
          +── change A
          +── change B
          +── change C
          |
          ↓
      one transaction
          |
       COMMIT
          ↓
    consistent state

If any required operation fails:

    change A
    change B
    change C
        ↓
      ROLLBACK
        ↓
    no partial logical operation committed

---

## 24.5 Transaction Boundary

Transaction boundaries shall follow meaningful logical operations rather than arbitrary individual SQL statements.

For example, if creating a Version requires:

- creating the Version record;
- establishing its required relationships;
- establishing required multilingual data;
- establishing required governance state;
- recording required audit information;

the complete operation should be evaluated as a single transactional unit where those changes must succeed together.

The exact workflow composition remains subject to implementation design.

---

## 24.6 Knowledge Asset and Initial Version

Where creation of a new Knowledge Asset requires creation of its initial Knowledge Asset Version, those changes should normally be performed within one transaction.

Conceptually:

    BEGIN

        create knowledge_asset

        create knowledge_asset_version

        establish required relationships

        establish required governance state

        record required audit information

    COMMIT

This prevents a partially created governed Knowledge Asset from becoming visible as a committed state without its required Version.

---

## 24.7 Version Creation

Version creation may require multiple related changes.

Where those changes together define the new Version as a valid governed state, they should be committed atomically.

The transaction shall work together with:

- Version uniqueness constraints;
- Current-Version protection;
- relationship integrity;
- multilingual integrity;
- governance integrity.

PAD-018 does not define the detailed Version workflow.

---

## 24.8 Current-Version Changes

A Current-Version change may require coordinated updates to multiple records.

The transaction strategy shall ensure that the transition from one Current Version to another does not expose an unintended intermediate committed state.

Conceptually:

    previous current version
            ↓
    new current version
            ↓
      atomic transaction
            ↓
      new consistent state

The exact enforcement mechanism remains subject to PAD-010, PAD-016, and PAD-019.

---

## 24.9 Relationship Changes

Where a logical relationship requires multiple physical writes, those writes shall be treated as one transactional operation when partial completion would violate the intended state.

For example:

    create relationship
        +
    create required relationship metadata
        +
    record required governance/audit information

may require one transaction.

The exact transaction boundary shall depend on the logical relationship and workflow.

---

## 24.10 Evidence and Provenance Operations

Where Evidence or Provenance changes require coordinated updates to governed data, those changes shall be transactionally consistent.

A transaction should prevent situations such as:

- a relationship referencing an Evidence record that was not successfully created;
- a governed Evidence association being committed without its required parent;
- a required provenance record being omitted from an otherwise completed operation.

The exact workflow remains subject to detailed design.

---

## 24.11 Governance Operations

Governance operations that modify current governed state and require corresponding audit recording shall be evaluated as a single transactional operation where both changes are required for a valid committed result.

For example:

    change governance state
            +
    record governance event
            ↓
        one transaction

This helps prevent a committed governance change without the corresponding required audit record.

---

## 24.12 Audit Recording

Where audit recording is mandatory for a governed operation, the audit record shall be committed consistently with the operation it records.

The baseline principle is:

    governed change
          +
    required audit record
          ↓
      same transaction

This prevents the database from containing a successful governed change with a missing mandatory audit event.

The exact audit architecture remains subject to detailed design.

---

## 24.13 Transaction Scope

Transactions should be:

- sufficiently broad to preserve logical atomicity;
- sufficiently narrow to avoid unnecessary lock duration and resource consumption.

Long-running transactions shall be avoided where possible.

Transactions should not encompass:

- lengthy external network calls;
- user interaction;
- unnecessary application processing;
- unrelated operations.

External work should generally occur outside the database transaction unless the workflow specifically requires a different architecture.

---

## 24.14 Transaction Failure

If a required operation fails because of:

- a constraint violation;
- serialization/concurrency failure;
- application error;
- database error;

the transaction shall not leave a partially committed logical operation.

The application/service layer shall handle transaction failure appropriately and determine whether the operation should be retried, corrected, or surfaced as an error.

Retry behavior for concurrency failures is addressed further by PAD-019.

---

## 24.15 Transaction and Validation

Application validation should occur before or during a transaction as appropriate.

However, application validation shall not replace database integrity enforcement.

The transaction provides the atomic persistence boundary, while PAD-016 provides the structural integrity boundary.

---

## 24.16 Transaction and Migrations

PAD-007 establishes version-controlled database migrations.

Where PostgreSQL supports safe transactional execution of a schema change, migrations should use transactional behavior where appropriate.

Migration operations that cannot safely or practically be executed within a transaction shall receive explicit implementation treatment.

This does not change the runtime transaction strategy.

---

## 24.17 Transaction and Indexing

Indexes established under PAD-017 affect transaction performance because index maintenance occurs during writes.

The transaction strategy shall therefore avoid unnecessary write amplification caused by excessive indexing.

PAD-018 does not determine the index inventory.

---

## 24.18 Options Considered

### Option A — Logical-Operation Transactions

**Assessment:** Preferred.

Group related changes that constitute one logical operation into a single database transaction.

---

### Option B — One Transaction Per SQL Statement

**Assessment:** Rejected as the baseline.

Individual statements may succeed while related statements fail, creating partial logical operations.

---

### Option C — Large Long-Lived Transactions

**Assessment:** Rejected.

Long-lived transactions increase:

- lock duration;
- resource usage;
- contention;
- operational complexity.

---

### Option D — Application-Level Compensation Instead of Transactions

**Assessment:** Rejected as the baseline.

Compensating operations cannot provide the same atomicity guarantees as a database transaction and can introduce additional failure states.

---

## 24.19 Rationale

The Knowledge Data Layer must not expose partially completed governed operations as valid committed states.

PostgreSQL transactions provide a natural boundary for ensuring atomicity while keeping the database responsible for persistence consistency.

The architecture therefore favors:

    meaningful logical transaction
              +
    database integrity
              +
    controlled concurrency

rather than attempting to reconstruct atomicity through application-level compensation.

---

## 24.20 Consequences

### Positive

- atomic multi-record operations;
- reduced partial-state risk;
- stronger consistency;
- clear persistence boundaries;
- simpler failure handling.

### Negative

- poorly designed transactions can increase contention;
- transaction boundaries require workflow analysis;
- retries may be required for some concurrency failures;
- long-running transactions must be actively avoided.

These trade-offs are acceptable.

---

---

# 25. PAD-019 — Concurrency Strategy

**Decision Area:** Concurrency Strategy
**Status:** Accepted
**Decision Date:** 2026-08-29

## 25.1 Decision

The ASM Brain Knowledge Data Layer shall use PostgreSQL's transactional concurrency mechanisms as the primary foundation for protecting governed data from conflicting concurrent operations.

The baseline concurrency strategy shall prefer:

- database-enforced integrity constraints;
- short, well-defined transactions;
- PostgreSQL's normal transaction isolation behavior;
- explicit row-level locking only where a demonstrated coordination requirement exists;
- optimistic conflict detection where appropriate;
- controlled retry behavior for transient concurrency failures.

The physical architecture shall avoid unnecessary global or coarse-grained locking.

Concurrency controls shall be introduced according to the specific invariant and access pattern being protected.

The exact PostgreSQL isolation level, locking patterns, retry policy, and workflow-specific concurrency mechanisms shall be finalized during detailed implementation design.

---

## 25.2 Context

ASM Brain will eventually support multiple users, services, workflows, and potentially automated processes interacting with the Knowledge Data Layer.

Concurrent operations may attempt to modify the same governed information.

Examples include:

- two users creating or modifying Versions;
- simultaneous Current-Version changes;
- concurrent taxonomy relationship updates;
- concurrent governance actions;
- simultaneous Evidence or Provenance updates;
- competing administrative operations.

Without an explicit concurrency strategy, application behavior could produce race conditions even when individual transactions are correctly implemented.

---

## 25.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-009 — Version Physical Representation;
- PAD-010 — Current-Version Protection;
- PAD-016 — Integrity Constraint Strategy;
- PAD-018 — Transaction Strategy.

PAD-019 builds upon the transaction and integrity principles already established.

---

## 25.4 Concurrency Principle

The baseline principle is:

    concurrent operation
            ↓
    PostgreSQL transaction
            ↓
    integrity protection
            ↓
    conflict detection
            ↓
    commit OR controlled failure/retry

Concurrency control should protect actual invariants rather than attempting to prevent all concurrent activity.

The database should allow safe concurrent operations wherever they do not conflict.

---

## 25.5 Normal Concurrent Operations

Operations that modify unrelated records should normally be allowed to proceed concurrently.

For example:

    User A → Knowledge Asset A
    User B → Knowledge Asset B

should not require a global database lock.

The physical architecture shall favor fine-grained concurrency rather than unnecessary serialization.

---

## 25.6 Conflicting Operations

When two operations modify the same governed state or compete for the same invariant, the database and transaction design must ensure that an invalid committed state cannot result.

For example:

    Operation A → Version 5 becomes current
    Operation B → Version 6 becomes current

The system must prevent concurrent execution from producing an invalid Current-Version state.

The exact mechanism may involve:

- constraints;
- row-level locking;
- transaction isolation;
- conflict detection;
- controlled retry.

The appropriate mechanism shall depend on the specific invariant.

---

## 25.7 Current-Version Concurrency

Current-Version protection is a key concurrency-sensitive operation.

Where multiple transactions may attempt to change the Current Version of the same Knowledge Asset, the physical design must ensure that concurrent operations cannot bypass the invariant established by PAD-010.

The implementation may require coordination around the relevant Knowledge Asset row or another appropriate database-level mechanism.

The exact locking and isolation strategy remains subject to detailed design.

---

## 25.8 Version Sequence Concurrency

PAD-009 requires the Version sequence to be unique within a Knowledge Asset.

Concurrent Version creation must therefore account for the possibility that two transactions attempt to allocate the same sequence position.

The database uniqueness requirement shall remain authoritative.

The application should be prepared to handle a concurrency conflict rather than assuming that a precomputed sequence value is always safe.

The exact sequence-allocation mechanism shall be finalized during implementation design.

---

## 25.9 Relationship Concurrency

Concurrent relationship changes should be allowed where they do not conflict.

Where two operations attempt to create the same unique relationship, database-level uniqueness should prevent duplicate committed state.

Where two operations modify conflicting relationship attributes, the appropriate concurrency behavior shall depend on the logical semantics of that relationship.

---

## 25.10 Governance Concurrency

Governance operations may be more sensitive than ordinary content changes.

For example:

    Operation A → approve Version
    Operation B → retire Version

If both operations are possible concurrently, the resulting state must remain consistent with the approved lifecycle and governance rules.

PAD-019 establishes that such operations require explicit concurrency consideration.

The exact transition and locking strategy remains subject to implementation design.

---

## 25.11 Evidence and Provenance Concurrency

Evidence and Provenance updates should generally use normal transactional concurrency unless the logical model establishes a specific conflict requirement.

Independent evidence additions should not unnecessarily block one another.

Where two operations modify the same governed Evidence or Provenance record, appropriate conflict handling shall be applied.

---

## 25.12 Audit Concurrency

Audit events are naturally append-oriented.

Independent audit events should be capable of being recorded concurrently without requiring global serialization.

Audit ordering shall therefore not depend on a single globally serialized application process unless the logical model explicitly requires such ordering.

Database timestamps and/or other appropriate identifiers may provide event ordering information.

The exact audit ordering model remains subject to detailed design.

---

## 25.13 Optimistic Concurrency

Optimistic concurrency should be preferred where conflicts are relatively uncommon and the system can safely detect conflicting changes.

Conceptually:

    read state
       ↓
    perform work
       ↓
    attempt update
       ↓
    detect conflict
       ↓
    retry or reject

This approach can reduce unnecessary locking.

The exact implementation mechanism, such as version or timestamp comparison, remains subject to physical and application design.

---

## 25.14 Pessimistic Locking

Explicit row-level locking may be used when concurrent operations must coordinate around a shared invariant and optimistic detection alone is insufficient.

Locking should be:

- as narrow as practical;
- held for the shortest practical duration;
- applied only to the records necessary for the invariant.

Global table-level locking should not be the normal application strategy.

---

## 25.15 Isolation Level

PAD-019 does not yet prescribe a final PostgreSQL transaction isolation level.

The final choice shall consider:

- required consistency;
- workload;
- contention;
- performance;
- retry characteristics;
- specific workflow requirements.

The baseline should avoid selecting a stronger isolation level merely because it appears safer.

The least restrictive level that reliably preserves the required invariants should be preferred.

---

## 25.16 Deadlock Consideration

Where explicit locking is used, the implementation shall minimize deadlock risk by:

- keeping transactions short;
- locking records in a consistent order;
- avoiding unnecessary locks;
- handling PostgreSQL deadlock errors appropriately.

The detailed deadlock handling policy remains subject to implementation design.

---

## 25.17 Retry Strategy

Some concurrency failures are transient and may be safely retried.

Examples may include:

- serialization failures;
- deadlocks;
- unique-constraint conflicts caused by concurrent allocation attempts.

The application/service layer should distinguish retryable failures from permanent validation or integrity errors.

Automatic retry shall not be applied indiscriminately.

The exact retry policy remains subject to implementation design.

---

## 25.18 Concurrency and Integrity

Concurrency control does not replace database integrity.

The baseline hierarchy is:

    Database constraints
          ↓
    authoritative invariant

    Transactions
          ↓
    atomic operation

    Concurrency strategy
          ↓
    safe behavior under simultaneous operations

All three layers work together.

---

## 25.19 Concurrency and Transactions

PAD-018 establishes the transaction boundary.

PAD-019 determines how those transactions behave when multiple transactions operate simultaneously.

A transaction that is correct in isolation may still require concurrency coordination when another transaction modifies the same governed state.

---

## 25.20 Options Considered

### Option A — Database-Centered Concurrency

**Assessment:** Preferred.

Use PostgreSQL transactions, constraints, appropriate locking, and conflict detection as the primary concurrency foundation.

---

### Option B — Application-Only Concurrency Control

**Assessment:** Rejected.

Application-only locking or coordination can be bypassed by other services, administrative operations, migrations, or future applications.

The database must remain capable of protecting authoritative invariants.

---

### Option C — Global Serialization

**Assessment:** Rejected.

Serializing all Knowledge Data Layer writes would unnecessarily reduce scalability and create a major contention point.

---

### Option D — Lock Everything

**Assessment:** Rejected.

Excessive locking increases contention, reduces throughput, and complicates operations.

---

## 25.21 Rationale

ASM Brain must support concurrent work without sacrificing the integrity of governed knowledge.

A database-centered strategy allows independent operations to proceed concurrently while requiring explicit coordination only when operations compete for the same governed state or invariant.

This provides a better balance between:

- correctness;
- concurrency;
- scalability;
- maintainability.

---

## 25.22 Consequences

### Positive

- safe concurrent operations;
- reduced unnecessary blocking;
- protection of critical invariants;
- better scalability;
- clearer separation of integrity, transactions, and concurrency.

### Negative

- concurrency conflicts must be handled;
- some operations may require retries;
- locking strategies require careful implementation;
- race conditions require explicit testing.

These trade-offs are accepted.

---

## 25.23 Relationship to PAD-009

PAD-009 establishes Version identity and per-parent Version sequence uniqueness.

PAD-019 ensures that concurrent Version creation cannot bypass those integrity requirements.

---

## 25.24 Relationship to PAD-010

PAD-010 establishes Current-Version protection.

PAD-019 identifies Current-Version changes as a concurrency-sensitive operation requiring explicit coordination.

---

## 25.25 Relationship to PAD-016

PAD-016 establishes database-level integrity.

PAD-019 ensures that those integrity requirements remain protected when multiple transactions operate concurrently.

---

## 25.26 Relationship to PAD-018

PAD-018 establishes transaction boundaries.

PAD-019 establishes the concurrency behavior of those transactions.

---

## 25.27 Scope Boundary

PAD-019 does not yet finalize:

- PostgreSQL isolation level;
- exact row-locking statements;
- lock ordering rules for every workflow;
- exact optimistic concurrency mechanism;
- retry counts;
- retry backoff;
- deadlock recovery implementation;
- connection-pool configuration;
- workload-specific concurrency tuning.

Those details remain subject to detailed implementation design.

---

## 25.28 Acceptance Criteria

PAD-019 is considered ready for acceptance when:

- [x] PostgreSQL transactions are established as the primary concurrency foundation.
- [x] Independent operations are allowed to proceed concurrently where safe.
- [x] Conflicting operations are explicitly recognized.
- [x] Current-Version changes are recognized as concurrency-sensitive.
- [x] Version sequence allocation is recognized as concurrency-sensitive.
- [x] Database uniqueness remains authoritative under concurrency.
- [x] Fine-grained locking is preferred over global serialization.
- [x] Optimistic concurrency is preferred where appropriate.
- [x] Explicit row-level locking is available where required.
- [x] Deadlock risk is explicitly recognized.
- [x] Retryable and non-retryable failures are distinguished conceptually.
- [x] Final isolation level remains subject to detailed design.
- [x] Exact locking and retry mechanisms remain subject to implementation design.
- [x] Architecture review completed.
- [x] Decision formally accepted into the final physical design.

# 26. PAD-020 — Initialization Strategy

**Decision Area:** Initialization Strategy
**Status:** Accepted
**Decision Date:** 2026-08-29

## 26.1 Decision

The ASM Brain Knowledge Data Layer shall be initialized through version-controlled, repeatable database migrations and controlled seed/bootstrap processes rather than through manual production database configuration.

Initialization shall establish the minimum physical structures and controlled baseline data required for the Knowledge Data Layer to operate in a valid state.

The initialization strategy shall distinguish between:

- structural initialization;
- required reference or controlled baseline data;
- optional development/test data;
- production content.

Structural initialization shall be performed through the migration mechanism established by PAD-007.

Required baseline data shall be introduced through controlled, versioned seed or bootstrap mechanisms where appropriate.

Production Knowledge Assets and other governed content shall not be embedded indiscriminately into the database initialization process.

Initialization shall be repeatable across supported environments to the extent practical.

---

## 26.2 Context

The physical architecture must provide a reliable method for creating a new ASM Brain Knowledge Data Layer environment.

A new environment may include:

- development;
- testing;
- staging;
- production;
- disaster-recovery or replacement environments.

Manual creation of tables, constraints, indexes, or baseline records would make environments difficult to reproduce and could introduce configuration drift.

PAD-007 already establishes migrations as the authoritative mechanism for structural changes.

PAD-020 defines how initialization uses that migration boundary to establish a valid starting state.

---

## 26.3 Source Basis

This decision is based on:

- P2-02.2 — Detailed Knowledge Data Model Specification v1.0;
- P2-02.3 — Scope & Design Brief;
- P2-02.3 — Physical Design Decision Framework;
- P2-02.3 — Physical Requirements Reconciliation;
- PAD-004 — PostgreSQL Extensions;
- PAD-006 — Schema Ownership;
- PAD-007 — Migration Boundary;
- PAD-016 — Integrity Constraint Strategy;
- PAD-017 — Indexing Strategy;
- PAD-018 — Transaction Strategy;
- PAD-019 — Concurrency Strategy.

PAD-020 completes the baseline physical architecture decision set by defining how a valid physical environment is initially established.

---

## 26.4 Initialization Principle

The baseline principle is:

    version-controlled source
             ↓
        migrations
             ↓
    physical database structure
             ↓
    controlled baseline data
             ↓
       valid environment

The initialization process shall be deterministic and reproducible to the extent practical.

---

## 26.5 Structural Initialization

Structural initialization shall establish the physical structures required by the approved architecture, including where applicable:

- PostgreSQL database boundary;
- ASM Brain Knowledge Data Layer schema;
- tables;
- primary keys;
- foreign keys;
- unique constraints;
- check constraints;
- indexes;
- other approved physical structures.

These structures shall be created through version-controlled migrations.

The initialization process shall not depend on manual SQL execution as the normal method.

---

## 26.6 Schema Ownership Initialization

PAD-006 establishes controlled schema ownership.

Initialization shall therefore create or configure the schema and structural objects under the approved ownership model.

Runtime application identities shall not become the owners of structural database objects merely because they execute application workloads.

The exact database-role provisioning mechanism remains an implementation concern.

---

## 26.7 Migration-Based Initialization

A new environment shall be capable of reaching the current approved physical schema by applying the required migration sequence from an appropriate baseline.

Conceptually:

    empty database
          ↓
    migration 001
          ↓
    migration 002
          ↓
          ...
          ↓
    current schema

The migration sequence shall remain version-controlled and reviewable.

---

## 26.8 Baseline Reference Data

Some structures may require baseline records before the application can operate correctly.

Examples may include:

- controlled system values;
- required taxonomy metadata;
- system-defined reference values;
- other explicitly approved baseline records.

Such data shall be introduced through controlled and repeatable seed/bootstrap mechanisms.

Baseline data shall be distinguished from ordinary governed Knowledge Assets.

---

## 26.9 Taxonomy Initialization

Taxonomy Concepts may require an initial controlled vocabulary or system-defined taxonomy structure.

Where such baseline taxonomy data is required for system operation, it shall be initialized through a controlled process.

The initialization mechanism shall preserve the governed nature of the taxonomy.

Large or evolving production taxonomy datasets should not be treated as immutable schema migration content merely for convenience.

The exact taxonomy loading strategy remains subject to detailed implementation design.

---

## 26.10 Controlled Vocabulary Initialization

Where PAD-016 results in reference-table-based controlled vocabularies, the required baseline reference values shall be initialized consistently across supported environments.

Reference data changes shall be version-controlled where they are part of the system's required baseline behavior.

The exact division between migrations and seed data shall be determined according to the nature and lifecycle of each dataset.

---

## 26.11 Development and Test Data

Development and test environments may require synthetic or representative datasets.

Such data shall be kept separate from production governed content.

Development/test seed data should be:

- reproducible;
- clearly identified;
- safe to reset;
- independent of production data unless explicitly authorized.

Production Knowledge Assets shall not be copied into development or test environments merely as a convenience.

Where production-derived data is required for testing, appropriate data-governance and privacy controls shall apply.

---

## 26.12 Production Content

Production Knowledge Assets shall not be treated as database schema initialization data.

The distinction is:

    Schema
        → initialized through migrations

    Required reference data
        → initialized through controlled seed/bootstrap

    Governed production content
        → introduced through approved application/governance workflows

This preserves the separation between physical architecture and Knowledge operations.

---

## 26.13 Initialization and Permissions

Initialization requires privileges that normal runtime identities should not possess.

Consistent with PAD-006 and PAD-007:

- structural initialization shall use a controlled administrative/migration identity;
- runtime application identities shall receive only required operational privileges;
- schema ownership shall remain outside normal runtime ownership.

The exact role and permission model remains subject to implementation design.

---

## 26.14 Initialization and Transactions

Where initialization operations can safely be executed transactionally, transactional execution should be preferred.

This helps prevent partially initialized structures or baseline data from being treated as a valid environment.

However, PostgreSQL operations that cannot safely or practically participate in one transaction shall receive explicit implementation treatment.

---

## 26.15 Initialization Validation

An initialization process shall include validation that the resulting environment satisfies the approved physical architecture.

Validation should confirm, where applicable:

- required schema exists;
- required entities exist;
- primary keys exist;
- foreign keys exist;
- required constraints exist;
- required indexes exist;
- required baseline reference data exists;
- ownership and permissions follow the approved model.

Initialization should fail clearly when required conditions are not satisfied.

---

## 26.16 Repeatability

The same approved migration and initialization process should produce materially equivalent physical environments across supported environments.

Environment-specific configuration should be externalized rather than embedded into structural migrations where possible.

This reduces configuration drift and improves maintainability.

---

## 26.17 Idempotency and Re-runs

Initialization mechanisms should be designed so that an already-initialized environment can be safely recognized and brought to the required migration state without blindly recreating existing structures.

Migration tooling should maintain authoritative migration state.

Seed/bootstrap mechanisms shall distinguish between:

- inserting required missing baseline data;
- updating controlled reference data;
- intentionally immutable baseline data.

The exact implementation mechanism remains subject to migration tooling design.

---

## 26.18 Initialization and Backup/Recovery

Initialization shall complement, not replace, backup and recovery procedures.

A recoverable environment may be restored from:

- database backup;
- infrastructure recovery;
- migration-based reconstruction;
- controlled baseline data restoration.

The detailed backup and disaster-recovery strategy is outside PAD-020.

---

## 26.19 Initialization and Audit

Initialization operations that create governed baseline structures or data shall be distinguishable from ordinary runtime governance operations.

Where audit recording is required for baseline governed data, the initialization mechanism shall follow the approved audit requirements.

Schema creation itself shall remain a migration/administrative operation rather than an ordinary Knowledge governance event.

---

## 26.20 Options Considered

### Option A — Migration-Based Initialization

**Assessment:** Preferred.

Use version-controlled migrations as the authoritative mechanism for structural initialization.

- reproducible;
- reviewable;
- traceable;
- consistent with PAD-007;
- suitable for multiple environments.

- configuration drift;
- undocumented changes;
- inconsistent environments;
- difficult recovery;
- poor reproducibility.

**Assessment:** Rejected.

This would conflict with PAD-006 and PAD-007.

---

### Option D — Full Production Dataset as Migration Content

**Assessment:** Rejected.

Production Knowledge Assets are governed content, not schema initialization data.

Embedding them into migrations would create unnecessary coupling between database structure and Knowledge operations.

## 26.21 Rationale

A sustainable platform needs environments that can be recreated reliably.

Migration-based initialization provides a clear chain:

    approved architecture
          ↓
    version-controlled migration
          ↓
    reproducible physical database

Separating schema initialization, baseline reference data, and governed production content keeps the architecture maintainable and prevents the migration system from becoming a content-management mechanism.
