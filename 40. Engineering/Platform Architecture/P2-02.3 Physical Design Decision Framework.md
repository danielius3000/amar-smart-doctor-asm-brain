# 1. Purpose

This document establishes the decision framework that will govern the physical design of the ASM Brain Knowledge Data Layer.

Its purpose is to ensure that physical implementation decisions are:

- derived from approved architecture;
- derived from the approved logical data model;
- requirements-driven;
- evidence-based;
- explicitly documented;
- reviewable;
- reversible where practical;
- free from unnecessary technology bias.

This framework exists between the approved logical model and the final physical data design.

The sequence is:

    P2-02.1
    Data-Layer Architecture
            ↓
    P2-02.2
    Approved Logical Data Model
            ↓
    P2-02.3 Scope & Design Brief
            ↓
    P2-02.3 Physical Design Decision Framework
            ↓
    P2-02.3 Physical Data Design
            ↓
    Architecture Review
            ↓
    Approval
            ↓
    Implementation Readiness

# 4. Physical Design Objectives

The physical design must optimize for the following order:

1. Correctness
2. Governance
3. Data integrity
4. Historical integrity
5. Maintainability
6. Appropriate performance
7. Operational reliability
8. Future scalability

The design must not optimize prematurely for:

- theoretical massive scale;
- fashionable technologies;
- unnecessary distributed architecture;
- speculative workloads;
- unnecessary polyglot persistence;
- premature search infrastructure;
- premature AI infrastructure.

# 5. Decision Categories

The physical design must explicitly address the following decision categories.

## 5.1 Storage Architecture

Determine the appropriate primary persistence architecture for governed Knowledge Data.

Questions:

- What storage model best represents the approved logical model?
- What consistency guarantees are required?
- What transactional guarantees are required?
- What relationship patterns must be supported?
- What operational complexity is acceptable?
- Does one primary storage technology satisfy the requirements?

Default principle:

> Prefer one primary persistence technology unless a clear requirement demonstrates that another technology is necessary.

---

## 5.2 Database Technology

Database technology must be evaluated against requirements rather than preference.

Evaluation criteria should include:

- relational integrity;
- transaction support;
- referential integrity;
- structured data support;
- JSON/document support where required;
- indexing capability;
- migration support;
- backup and recovery capability;
- operational maturity;
- ecosystem maturity;
- developer maintainability;
- hosting/deployment practicality;
- expected workload;
- future API integration;
- future search integration;
- future AI integration;
- total operational complexity.

The decision must document:

- selected technology;
- alternatives considered;
- reasons for selection;
- rejected alternatives;
- consequences;
- unresolved risks.

# 7. Identifier Strategy

The physical identifier strategy must be evaluated independently from logical identity.

P2-02.2 deliberately leaves the physical identifier mechanism open.

Candidate approaches may include:

- UUID;
- ULID;
- database-generated integer;
- another suitable stable identifier mechanism.

Evaluation criteria:

- global uniqueness;
- stability;
- generation model;
- indexing characteristics;
- storage efficiency;
- API suitability;
- distributed-system suitability;
- readability;
- migration implications;
- operational simplicity.

The final decision must distinguish:

**Logical Identity**

from

**Physical Storage Identifier**

where such distinction is necessary.

No physical identifier may replace or alter governed logical identity semantics.

---

# 8. Knowledge Asset Physical Design

The physical design must preserve the distinction between:

**Knowledge Asset**

and

**Knowledge Asset Version**.

The Knowledge Asset physical structure should represent stable identity and asset-level properties.

It must not become a generic content table containing every version-specific property.

Questions:

- Which properties belong to the stable asset?
- Which properties belong to a version?
- How is current-version resolution represented?
- How is stable identity enforced?
- How are asset-level governance relationships represented?

---

# 9. Knowledge Asset Version Physical Design

The physical design must preserve historical versionability.

Questions:

- How is the parent Knowledge Asset represented?
- How is version identity represented?
- How is version ordering enforced?
- How is the current version resolved?
- How are historical versions retained?
- How is approved-version immutability protected?
- How are lifecycle states represented?
- How are temporal properties represented?

The design must allow retrieval of a specific historical version.

---

# 10. Versioning Decision

The physical design must determine:

- version identifier strategy;
- version sequence strategy;
- uniqueness within parent asset;
- current-version resolution;
- historical retrieval;
- approved-version protection;
- supersession representation.

The following logical principle is mandatory:

> A substantive change creates a new Knowledge Asset Version rather than silently rewriting an approved version.

The physical design must support this rule.

---

# 11. Lifecycle Representation

The physical design must represent the governed lifecycle without inventing unsupported states.

The baseline logical lifecycle includes:

- Draft
- In Review
- Approved
- Published
- Superseded
- Retired

The design must determine:

- where lifecycle state is stored;
- whether lifecycle state belongs to the version, asset, or both;
- how invalid transitions are prevented;
- how historical transitions are preserved;
- how current state is resolved.

Lifecycle semantics must remain consistent with P2-02.2 and governing standards.

---

# 12. Taxonomy Concept Physical Design

Taxonomy Concept requires particular care because it represents governed conceptual identity rather than content.

The physical design must determine:

- concept identifier;
- concept type;
- preferred term;
- multilingual representation;
- synonyms;
- concept status;
- taxonomy membership;
- parent/child relationships where applicable;
- concept relationship representation.

The design must not introduce a generic `MedicalConcept` entity merely for implementation convenience.

Any deviation from the approved logical taxonomy model requires formal review.

---

# 13. Taxonomy Hierarchy

The physical design must evaluate how taxonomy relationships are represented.

Potential approaches may include:

- adjacency-list relationships;
- closure-table structures;
- materialized-path structures;
- another justified representation.

The choice must be driven by:

- expected hierarchy depth;
- traversal patterns;
- update frequency;
- query requirements;
- governance requirements;
- maintainability.

No hierarchy optimization should be introduced without a demonstrated requirement.

---

# 14. Multilingual Representation

The physical design must preserve the logical principle that language representation is distinct from identity.

The design must determine:

- where language is represented;
- how language-specific terms are stored;
- how preferred terms are represented;
- how synonyms are represented;
- how multilingual retrieval can later be supported;
- whether language-specific metadata is required.

A language change must not unintentionally create a new governed identity.

---

# 15. Knowledge Representation

P2-02.2 deliberately avoids reducing governed knowledge to a generic `content` field.

The physical design must therefore determine an appropriate representation for structured knowledge.

Questions:

- Which knowledge components require structured fields?
- Which components may require flexible structured data?
- Which components require strict schema?
- Where is controlled flexibility justified?
- How will schema evolution be governed?
- How will validation occur?

The physical design must avoid both extremes:

**Over-normalization**

and

**uncontrolled generic JSON/document storage**.

The appropriate balance must be requirements-driven.

---

# 16. Supporting Structures

Supporting structures may be required for:

- evidence;
- sources;
- provenance;
- relationships;
- dependencies;
- review;
- approval;
- governance;
- audit;
- multilingual representation;
- taxonomy relationships.

Each supporting structure must answer:

1. What requirement creates the need?
2. Which logical entity does it support?
3. What information does it preserve?
4. What integrity rules apply?
5. Is it authoritative knowledge or supporting metadata?
6. Does it belong in the primary database?
7. Could the requirement be satisfied more simply?

No supporting structure should be introduced merely because it is a common database pattern.

---

# 17. Evidence and Provenance

Evidence and provenance are core trust requirements.

The physical design must preserve the ability to answer:

- What evidence supports this knowledge?
- What source produced or supplied the evidence?
- Which governed knowledge version used that evidence?
- When was the evidence associated?
- What provenance information is available?
- Can the relationship be reconstructed historically?

Physical storage must not weaken traceability for the sake of schema simplicity.

---

# 18. Relationship Strategy

The physical design must determine how logical relationships are represented.

Candidate mechanisms include:

- foreign keys;
- associative tables;
- relationship entities;
- controlled relationship metadata.

The choice must depend on relationship semantics.

Relationships must not be represented merely as uncontrolled embedded identifier lists when governed relationship semantics require stronger integrity.

---

# 19. Integrity Constraint Strategy

The physical design must identify constraints for:

- primary keys;
- foreign keys;
- uniqueness;
- nullability;
- valid lifecycle values;
- valid version sequences;
- relationship integrity;
- required governance properties.

Each constraint must be classified as:

- domain rule;
- governance rule;
- integrity rule;
- implementation convenience.

Only genuine rules should be enforced as authoritative database constraints.

---

# 20. Indexing Strategy

Indexes must be derived from expected access patterns.

Initial access patterns should include:

- asset lookup by stable identity;
- version lookup;
- current-version resolution;
- taxonomy concept lookup;
- taxonomy traversal;
- relationship retrieval;
- lifecycle filtering;
- governance filtering;
- evidence retrieval;
- administrative queries.

Each major index should have a reason.

The design must avoid:

- indexing every column;
- speculative indexes;
- redundant indexes;
- premature optimization.

Index decisions should be revisited after real workload evidence becomes available.

---

# 21. Transaction Strategy

The physical design must identify important transactional boundaries.

Questions:

- Which operations must be atomic?
- Which changes must update multiple structures together?
- What constitutes a valid version creation transaction?
- What constitutes a valid approval transaction?
- What relationship updates require consistency?
- Which operations may be asynchronous?

The design should favor simple transactional boundaries unless stronger guarantees are genuinely required.

---

# 22. Concurrency Strategy

The physical design must consider concurrent operations such as:

- multiple editors;
- simultaneous review;
- approval;
- version creation;
- taxonomy updates;
- governance updates.

The design must determine where protection is required against:

- duplicate versions;
- conflicting updates;
- invalid state transitions;
- stale writes.

Concurrency mechanisms must be proportionate to actual requirements.

---

# 23. Migration Strategy

The physical design must define how the schema can evolve.

The migration strategy should address:

- versioned migrations;
- forward migration;
- rollback considerations;
- development/staging/production consistency;
- migration ordering;
- destructive-change controls;
- reference-data migrations;
- taxonomy migrations.

The migration system must be treated as part of the governed implementation process.

---

# 24. Initialization Strategy

Initial data must be distinguished into categories.

## 24.1 Schema

Database structures required for the system.

## 24.2 Reference Data

Controlled data required for operation.

Examples may include:

- taxonomy bootstrap data;
- controlled vocabularies;
- lifecycle values;
- system configuration.

## 24.3 Governed Knowledge

Actual governed Knowledge Assets and Knowledge Asset Versions.

These must not be treated as ordinary seed data.

The physical design must preserve the distinction between:

**system initialization**

and

**governed knowledge ingestion**.

---

# 25. Audit Strategy

The physical design must determine what audit information is required.

Questions:

- Which events must be auditable?
- Which governance actions require historical records?
- Which changes are already represented by versioning?
- Which technical events belong outside the knowledge data layer?
- What information is necessary to reconstruct governance history?

Audit storage must not become a duplicate copy of every database operation.

---

# 26. Retention Strategy

The physical design must identify retention requirements relevant to governed knowledge.

At minimum, consider:

- historical versions;
- retired knowledge;
- evidence relationships;
- provenance;
- governance history;
- audit information.

Deletion must not destroy required historical integrity.

Retention policies must follow governing requirements rather than database convenience.

# 28. Polyglot Persistence Decision

The default position is:

> One primary database unless a clear requirement proves that multiple storage technologies are necessary.

A second storage technology may be introduced only when:

1. a concrete requirement exists;
2. the primary storage cannot reasonably satisfy it;
3. the additional technology provides meaningful value;
4. operational complexity is understood;
5. ownership and synchronization are defined;
6. failure modes are understood.

Examples of technologies that should not be introduced merely because they may be useful later:

- vector databases;
- graph databases;
- document databases;
- dedicated search engines;
- specialized caches.

Future integration requirements may be recorded without implementing them now.

---

# 29. Search Boundary

P2-02.3 must remain separate from P2-05 Search & Retrieval.

The physical data design may define:

- identifiers required for future indexing;
- stable source records;
- metadata required for indexing;
- change-detection requirements;
- synchronization boundaries.

It must not implement:

- search ranking;
- semantic retrieval;
- search infrastructure;
- embedding pipelines.

---

# 30. AI Boundary

P2-02.3 must remain separate from P2-04 AI Workforce Infrastructure.

The physical data layer may provide authoritative structured data to future AI systems.

It must not:

- embed AI-specific storage assumptions into the governed model;
- introduce vector infrastructure prematurely;
- make model-specific data structures authoritative;
- allow AI-generated content to become authoritative without governance.

AI consumes governed knowledge.

AI does not define the knowledge model.

---

# 31. API Boundary

The physical design must support future API access without becoming an API design document.

Consider:

- stable identifiers;
- predictable relationships;
- version addressability;
- lifecycle filtering;
- governance filtering;
- efficient primary lookups.

Do not define API endpoints here.

# 33. Decision Classification

Each decision must be classified as one of:

### D1 — Physical Implementation Decision

Can be decided within P2-02.3 authority.

Examples:

- index choice;
- physical column type;
- migration tooling;
- constraint implementation.

### D2 — Architecture Decision

May affect P2-01 or P2-02.1.

Requires architecture review.

Examples:

- introducing another persistence technology;
- changing storage architecture;
- introducing a new architectural subsystem.

### D3 — Logical Model Decision

Changes P2-02.2 semantics.

Must return to logical-model review.

Examples:

- changing entity boundaries;
- changing identity semantics;
- changing version semantics;
- changing approved logical relationships.

### D4 — Governance Decision

Changes the governing knowledge or lifecycle model.

Must be escalated to the appropriate governance authority.

# 36. Evaluation Rules

All physical design options must be evaluated against these rules.

## Rule 1 — Correctness over convenience

A technically convenient solution must not weaken the governed model.

## Rule 2 — Simplicity over novelty

The simplest adequate solution is preferred.

## Rule 3 — Evidence over preference

Technology choices must be supported by requirements and evidence.

## Rule 4 — Reversible where practical

Early decisions should avoid unnecessary irreversible commitments.

## Rule 5 — Governance over optimization

Data governance and historical integrity take priority over storage optimization.

## Rule 6 — One source of truth

Physical implementation must not create competing authoritative representations of governed knowledge.

## Rule 7 — Future-ready, not future-built

Prepare for known future interfaces without implementing speculative infrastructure.

---

# 37. Physical Design Anti-Patterns

The following patterns should be actively rejected unless explicitly justified.

## 37.1 Generic Content Table

A single table containing all knowledge types without meaningful domain boundaries.

## 37.2 Database-Driven Domain Model

Allowing the database structure to redefine logical entities.

## 37.3 Premature Microservices

Splitting the data layer into services without a concrete requirement.

## 37.4 Premature Polyglot Persistence

Adding multiple databases without demonstrated need.

## 37.5 Premature Vector Database

Introducing vector storage before search/AI requirements justify it.

## 37.6 Uncontrolled JSON

Using flexible JSON structures where governed fields require explicit integrity.

## 37.7 Excessive Normalization

Creating excessive tables that make the governed model harder to understand without meaningful integrity benefits.

## 37.8 Excessive Denormalization

Duplicating authoritative data merely for anticipated performance.

## 37.9 Uncontrolled Embedded Relationships

Storing governed relationships as arbitrary identifier arrays without appropriate integrity.

## 37.10 Destructive Version Updates

Overwriting approved knowledge instead of creating a governed new version.

# 38. Physical Design Review Questions

Before approval, the engineering team must be able to answer:

### Architecture

- Does the design conform to P2-02.1?
- Does it remain within P2-01 boundaries?

### Logical Model

- Does every logical entity map correctly?
- Is stable identity preserved?
- Is version identity preserved?
- Are lifecycle semantics preserved?
- Are logical relationships preserved?

### Governance

- Can historical knowledge be reconstructed?
- Can evidence and provenance be traced?
- Can governance state be understood?

### Integrity

- Which database constraints protect the model?
- Which rules remain application-level?
- Are there risks of invalid states?

### Performance

- Which access patterns are optimized?
- Why does each important index exist?
- Are any optimizations premature?

### Operations

- Can the schema evolve safely?
- Can the data be backed up and restored?
- Can migrations be reproduced consistently?

### Maintainability

- Can a future engineer understand the design?
- Can the architecture evolve without unnecessary migration pain?

---

# 39. Implementation Readiness Test

The physical design should pass the following test:

> Could a competent engineering team implement the Knowledge Data Layer from the approved physical design without making undocumented architectural or logical-model decisions?

If the answer is **No**, the physical design is not ready.

If the answer is **Yes**, the design may proceed to formal architecture review.
