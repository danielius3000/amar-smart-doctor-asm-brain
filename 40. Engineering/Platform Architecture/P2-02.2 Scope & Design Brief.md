## 1. Purpose

P2-02.2 defines the scope, design objectives, decision areas, deliverables, and acceptance criteria for the Detailed Knowledge Data Model Specification.

Its purpose is to translate the approved P2-02.1 Knowledge Data Layer Architecture & Data Model Foundation into a sufficiently detailed logical data-model specification that subsequent physical data design and implementation can proceed without engineers having to invent fundamental knowledge-domain rules.

P2-02.2 is therefore a specification milestone.

It is not a production database implementation milestone.

## 5. Scope

P2-02.2 includes the detailed logical specification of the governed Knowledge Data Layer.

### 5.1 Entity Model

The specification will define the logical responsibilities and boundaries of the principal knowledge entities identified by P2-02.1, including where applicable:

- Knowledge Asset
- Knowledge Asset Version
- Medical Concept
- Taxonomy Node / Taxonomy Concept
- Taxonomy Relationship
- Evidence Record
- Source
- Knowledge Relationship
- Knowledge Dependency
- Review Record
- Approval Record
- Governance Record
- Provenance Record
- Audit Record

The final entity set may be refined where detailed analysis demonstrates that an identified logical concept should be represented differently.

Such refinement must be explicitly documented.

### 5.2 Identity Model

The specification will define:

- stable entity identity
- version identity
- identifier responsibilities
- uniqueness requirements
- identity persistence
- relationships between stable identity and version identity
- requirements for historical reference

### 5.3 Attribute Model

For each governed logical entity, the specification will define:

- purpose
- required attributes
- optional attributes
- attribute semantics
- controlled values where applicable
- ownership of attributes
- governance significance
- version sensitivity where applicable

### 5.4 Relationship Model

The specification will define:

- relationship types
- relationship direction
- relationship ownership
- cardinality
- required versus optional relationships
- relationship constraints
- dependency relationships
- historical preservation requirements

Relationship definitions must remain consistent with the approved knowledge relationship standards.

### 5.5 Lifecycle and Versioning

The specification will define the logical representation of:

- lifecycle state
- state transitions
- version creation
- version identity
- current version
- approved version
- historical versions
- retirement and archival states
- governance implications of lifecycle transitions

### 5.6 Evidence and Source Model

The specification will define:

- Source responsibilities
- Evidence Record responsibilities
- source-to-evidence relationships
- evidence-to-knowledge relationships
- evidence status requirements
- evidence provenance requirements
- evidence granularity

P2-02.2 must explicitly evaluate whether evidence association is required at:

- Knowledge Asset level
- assertion / claim level
- both levels

This decision must be based on the requirements of the Evidence Standard and actual knowledge representation needs.

P2-02.2 must not create a separate claim-level entity merely because such an entity may be useful unless the requirements justify it.

### 5.7 Provenance and Audit

P2-02.2 will preserve the architectural distinction between provenance and auditability.

Provenance describes:

- origin
- derivation
- lineage

Audit records describe:

- governed system events
- changes affecting governed objects
- relevant governance events

The specification will define the logical data requirements for both concerns without treating them as interchangeable.

### 5.8 Review, Approval, and Governance

The specification will define the data requirements necessary to represent:

- review activity
- review outcomes
- approval
- approval authority
- governance state
- governance actions
- relevant decision records

These structures must support the governance boundaries established by P2-01.

### 5.9 Taxonomy and Medical Concepts

The specification will define:

- medical concept identity
- taxonomy identity
- taxonomy membership
- taxonomy relationships
- concept-to-knowledge relationships
- required distinction between a medical concept and a knowledge asset

The data model must not collapse concepts and knowledge assets into a single uncontrolled object merely for implementation convenience.

### 5.10 Multilingual Representation

The specification will define requirements for multilingual knowledge representation, including:

- language identification
- language-independent identity where required
- localized representations
- relationships between language representations
- preservation of governed knowledge identity across languages

Bangla and English must be supported without creating unnecessary duplication of the underlying governed knowledge.

### 5.11 Integrity Constraints

The specification will define logical integrity requirements covering, where applicable:

- identity integrity
- version integrity
- lifecycle integrity
- relationship integrity
- dependency integrity
- evidence integrity
- governance integrity
- referential integrity
- historical integrity

### 5.12 Physical-Storage Requirements

P2-02.2 will identify the requirements that a future physical data design must satisfy.

It may evaluate candidate storage patterns at an architectural level.

It will not prematurely commit the project to a specific database technology unless such a decision is justified by approved architectural requirements.

Technology must follow the logical model and requirements rather than drive them.

## 7. Design Principles

P2-02.2 must follow these principles.

### 7.1 Knowledge First

The data model must represent governed knowledge rather than merely reflecting application screens or current user-interface requirements.

### 7.2 Standards First

S1-04 remains the source of truth for knowledge-system standards.

The data model must implement those standards rather than redefine them.

### 7.3 Stable Identity

Governed knowledge must have stable identity independent of individual versions or representations.

### 7.4 Explicit Governance

Governance state, review, approval, lifecycle, provenance, and audit requirements must be representable explicitly.

### 7.5 Historical Preservation

The model must preserve required historical knowledge states and relationships.

### 7.6 Controlled Relationships

Relationships must be governed and typed rather than represented as uncontrolled arbitrary links.

### 7.7 Technology-Neutral Logical Model

Logical knowledge requirements must be established before physical implementation technology is allowed to constrain them.

### 7.8 Multilingual by Design

Language representation must be part of the architecture rather than added later as an afterthought.

### 7.9 Evidence-Aware

The model must support traceability between governed knowledge and its supporting evidence at the appropriate granularity.

### 7.10 Minimal Necessary Complexity

The model should introduce an entity, relationship, or abstraction only when justified by knowledge, governance, integrity, or operational requirements.

## 13. Expected Outcome

The expected outcome of P2-02.2 is a stable, governed, implementation-ready logical Knowledge Data Model.

An engineer reviewing the approved specification should be able to understand:

- what the core knowledge objects are;
- what each object represents;
- how objects relate;
- how objects are identified;
- how versions are represented;
- how knowledge progresses through lifecycle states;
- how evidence is associated;
- how provenance is represented;
- how auditability is represented;
- how review and approval are represented;
- how taxonomy and medical concepts are represented;
- how multilingual knowledge is represented;
- what integrity rules must be enforced;
- what requirements the physical data layer must satisfy.

The engineer should not need to invent fundamental knowledge-domain boundaries or governance rules.

## 15. Decision Discipline

P2-02.2 must distinguish clearly between:

- approved architectural decisions;
- new design decisions;
- explicit assumptions;
- deferred decisions;
- implementation decisions.

No implementation constraint should be introduced merely because it is convenient for an early prototype.

Where multiple viable approaches exist, the selected approach must be justified against:

- knowledge requirements;
- governance requirements;
- maintainability;
- integrity;
- scalability;
- implementation complexity;
- long-term platform evolution.
